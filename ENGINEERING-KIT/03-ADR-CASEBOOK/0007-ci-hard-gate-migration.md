# ADR-0007: CI 从软门全改硬门

- **状态**：已接受
- **日期**：2026-10-23
- **决策者**：项目组
- **证据分级**：【已验证】
- **项目**：某 2026 年桌面应用项目（下文统称「该项目」）

---

## 背景

某桌面应用项目收官冲刺期间，后端测试长期处于「软门」状态——CI 会跑但失败不阻塞合并。原因：

1. pytest 存在陈旧断言，覆盖旧接口形态；
2. 部分用例偶发失败（约 1/16 概率炸）——测试代码带随机性未收敛；
3. 若干依赖声明缺失，导致 clean 环境 import 失败；
4. Node 版本下限与前端工具链 `engines` 字段不一致。

收官阶段面临两个压力：

1. **对外发布前必须 CI 全绿**——公开仓库不接受「本地过 CI 挂」的历史；
2. **质量信号可信度**：CI 全绿是「源码可运行」的可信度证据。

## 决策

**CI 从软门全改硬门**：所有后端 pytest、云端服务测试、license 护栏测试、依赖声明闸门、安全扫描、ESLint 全部纳入 `required status checks`，任一失败即阻塞合并。

**落地顺序**（该项目实际走过的路径）：

1. 修后端 pytest 陈旧断言 / 陈旧接口，软门转硬门；
2. 修云端服务用例的偶发失败（1/16 概率炸）——找到随机性根因并消除；
3. 把 license 护栏测试纳入 CI 硬门 + 修一条早已失效的路由枚举用例；
4. CI Node 20 → 22（前端工具链 `engines` 要求 ≥ 22.19.0）；
5. 补齐依赖声明 + 新增依赖声明闸门（双向自测）；
6. ESLint 全量检查清零；
7. 修后端 ruff 若干 NameError。

**8 硬门清单**：见 `.github/workflows/ci.yml`（本手册姊妹篇 `02-GIT-LIFECYCLE-SPEC.md` §7.1 有完整表）。

## 否掉了什么

| 方案 | 为什么否 |
|---|---|
| 保留软门，靠人工 review 兜底 | 对外发布前 CI 全绿是社区贡献的信任前提 |
| 只修最紧急的软门（后端 pytest） | 依赖声明闸门、安全扫描、ESLint 都是硬门；漏任何一处都会回归 |
| 用 `continue-on-error: true` 局部放行 | 等于把软门换了个名字，长期看不解决 |
| 用 `--allow-failures` GitHub Actions 语法 | 同上；且 `required status checks` 里被跳过的 check 会导致 GitHub 显示 warning |
| 把 CI 拆成「阻塞 + 非阻塞」两条 workflow | 复杂度上升，且开源义务要求提供「可运行」的源码；两条 workflow 语义模糊 |

## 代价

**收益**：
- 对外发布前 CI 全绿，社区贡献可信
- 开源义务履行有 CI 证据链
- 每次提交都跑全量测试，回归早发现

**代价**：
- 修 8 硬门共 7 个 commit
- CI 运行时间从软门时代的「快但不可信」变成「慢但可信」（8 硬门串跑）
- 后续任何 CI 变更都必须评估是否会破坏硬门

**已知副作用**：
- 依赖声明闸门必须带 `--self-test` 反向自测（逐个删掉候选包的声明，要求它们必须被重新报出来），否则闸门失灵
- 偶发失败用例的测试代码仍需注意随机性

## 未来复审触发条件

- CI 运行时间超过 15 分钟，需拆分并行化
- 引入新语言 / 新测试框架（需评估是否纳入硬门）
- 社区贡献者反馈 CI 过严（需评估放宽某硬门的门槛）

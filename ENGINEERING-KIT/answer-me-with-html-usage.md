# answer-me-with-html 使用规范（laoma 定制版）

> 适用：所有「分析报告 / 评审 / 方案对比 / 架构讲解」类 HTML 页面产出。
> 基础 skill：[QingYunA/answer-me-with-html](https://github.com/QingYunA/answer-me-with-html)（MIT），
> 已装入 `C:/Users/Administrator/.agents/skills/answer-me-with-html/`，CLI 随 skill 自带，需 Node.js 20+。

## 0. 新电脑部署（三步，约 5 分钟）

**skill 是本地可执行 CLI，只读本规范渲染不出页面——每台跑 Agent 的电脑都要装一套。**

```bash
# 1. 确认 Node.js ≥ 20，没有就装：winget install OpenJS.NodeJS.LTS
node --version

# 2. 安装 skill（任选其一）
npx skills add QingYunA/answer-me-with-html -g -y
# 或手动：git clone --depth 1 https://github.com/QingYunA/answer-me-with-html
# cp -R answer-me-with-html/skills/answer-me-with-html <你的Agent的skills目录>/

# 3. 装 laoma 主题 + 打页头补丁（本仓库自带，见 §7 与 assets/）
mkdir -p ~/.answer-me-with-html/themes
cp ENGINEERING-KIT/assets/answer-me-with-html/laoma.json ~/.answer-me-with-html/themes/
# 然后按 §7 修改 am.mjs 的 colophon() 函数（页头只留日期）
# 验证：am theme check laoma → 0 errors 0 warnings；渲染测试页看页头只有日期
```

三步缺一不可：没 skill 没有 CLI；没主题退回蓝图蓝；没补丁页头带品牌行。

## 1. 主题：用 `laoma`，不用默认 blueprint

自建主题 `~/.answer-me-with-html/themes/laoma.json`（宣纸白 + 墨字 + 印泥红 #C9252D，
与标书产品正红品牌同源）。已过 `am theme check`（WCAG AA，light/dark 双套 0 警告）。

- 稿件 frontmatter 写 `theme: laoma`，或渲染时 `--theme laoma`
- 主题 CSS 已内置两条强调机制：
  - **加粗文字自动带红底衬线**（`linear-gradient` 下 38% 红衬）——关键数字、关键结论必须加粗
  - panel 编号、callout 左边框统一印泥红
- 改主题色值后必须跑 `am theme check laoma`，0 errors 0 warnings 才算过

## 2. 模板选择：分析类一律 `doc`，概览类才用 `sheet`

| 场景 | 模板 | 理由 |
|---|---|---|
| 报告深读 / 评审 / 调研结论（≥10 节） | `template: doc` + `outline: left` | 侧栏目录 + 线性长读，细节放得下 |
| 一屏速览 / 会议片头 / 日常结论 | `template: sheet`（默认） | 2~4 面板格子 |

教训（2026-11-12）：16-18 KB 的报告压进 sheet 的 7 个格子，用户评价
「层次够、构图够，但重点不突出、要点分析不细致」——深度内容必须用 doc。

## 3. 内容写法：重点突出的四条硬规则

1. **结论前置**：lead 一句话给结论 + 加粗关键数字；第一节是 callout 结论，不是背景。
2. **每节有钩子**：长节末尾放一个 `callout`（info/warn/err）说「所以呢」；
   纯表格节至少在表后留一行判断句。
3. **关键数字全部加粗**：星标数、金额、比例、天数、测试通过数——让扫读的人
   只看加粗字也能拿到全部重点。
4. **评审类必带「原文没写的部分」**：分析别人文档时，最后一节是评审者自己的
   增量判断（缺口/风险/排期建议），不是复述原文。

## 4. STE 与渲染纪律

- 渲染输出 `STE 0 warnings` 才算交付；警告按 CLI 给的行号修稿重渲（最多 2 轮）
- 中文句长：描述句 ≤45 字，步骤句 ≤35 字；一段 ≤6 句
- 敏感词自动拦截：闭环、方法论、赋能、综上所述等套话会报 cliché，改成具体事实
- 产物路径：标书项目一律 `-o "D:/dim开发/_bidmaster/网页/<名称>.html"`；
  稿件存 `~/.answer-me-with-html/drafts/`，不混进项目目录

## 5. 迭代已产出的页面

只改一节用 patch，不要整页重写：

```bash

```

## 6. 上游更新

`am theme update` 不会覆盖用户自建主题，升级安全。

## 7. 本地补丁记录（skill 升级后必须重打）

CLI 被改动过一处（MIT 允许）。`am.mjs` 的 `colophon()` 函数（搜 `function colophon`）：
原版输出「Generated by Answer me with HTML 0.5.x · 日期 · ★ Star on GitHub」，
本地改为**只输出日期**。补丁内容：

```js
function colophon(language) {
  const p2 = (n) => String(n).padStart(2, "0");
  const d2 = new Date();
  const time = language.dateOrder === "dmy"
    ? `${d2.getDate()}.${d2.getMonth() + 1}.${d2.getFullYear()}`
    : `${d2.getFullYear()}-${p2(d2.getMonth() + 1)}-${p2(d2.getDate())}`;
  return `<p class="am-colophon">${esc(time)}</p>`;
}
```

页头日期的正文字体由 laoma 主题 CSS 负责：`& .am-colophon { font-family: var(--font-sans); ... }`。
更新 skill 后检查产物页头，出现品牌行就说明补丁被覆盖，按上面重打。

## 8. 稿件持久化

CLI 渲染成功后会删除传入的草稿文件（无论 stdin 还是文件路径）。
正式产出一律把稿件存 `D:/dim开发/_bidmaster/网页/_drafts/<名>.md`，再渲染到同目录上级。
找回旧稿：页面 HTML 内嵌 `#am-source`（「复制源稿」按钮），或直接读 drafts 目录。

## 9. 全生命周期适配矩阵（产品全过程可视化）

对应 ENGINEERING-KIT / PROJECT-RUN 的文档体系。结论：**全过程可适配**，
组件覆盖足够，不需要再改 skill——缺的只是每类文档的稿件套路（recipe）。

| 生命周期阶段 | 文档类型 | 首选组件 | 状态 |
|---|---|---|---|
| 需求侧 | PRD / VISION | table（对比）· flow（架构）· ask（拍板项） | ok 已验证（PRD 深读页） |
| 敲定 | ADR / 决策台账 P#/D# | kv（决策元信息）· table（备选对比 ✓/✗）· flow（决策树） | ok |
| 开发 | 架构 / spec / BUILDSPEC | flow · er（数据模型）· sequence · api · tree · class | ok 组件全覆盖 |
| 开发 | 开发计划 / 里程碑 | timeline · limits · chart bar | ok |
| 巡检 | checklist / 审计 | table（状态列 ok/no/warn）· callout | ok |
| QA 质检 | 测试报告 / 评审流 | chart（通过率）· table（模块×结果）· callout（结论） | ok |
| 回测 | 回归报告 / 趋势 | chart line（历史通过数）· limits | ok |
| 缺陷 | bug 分析 / 修复计划 | annot（逐词标注）· diff（修复）· sequence（冲突时序）· flow（根因分支） | ok |
| 交付 | 项目说明书 / onboarding | doc 模板 · tree · code src=（引用真实代码行） | ok |
| 交付 | 深度设计原理 | doc 模板长文 · flow · annot | ok |
| 上线 | 上线报告 / 发版 | kv（版本元信息）· timeline · table（检查单） | ok |
| 运营 | 运营数据 / 授权 | chart · table sort filter | ok |

三条边界（什么时候**不**用 am 出页）：
- **超长清单**（如 60+ 条坑清单）：表格超过 24 行拆页或保留 MD，硬塞一页不可读
- **需要持续更新的活文档**（PROGRESS 台账、AGENT.md）：保留 MD，am 出的是快照页
- **代码评审正文**：diff 块适合展示结论，逐行评审仍走 PR 流程

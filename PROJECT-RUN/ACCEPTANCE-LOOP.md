# 验收闭环协议（Claim→Proof Gap 根治）

> 立规日期：2026-11-13 · 背景：两天内连续 4 起事故的模式完全相同——
> Agent 报告「已完成/已验证」，用户一用就炸。每次的借口都不同
> （子代理跑偏、测试环境差异、形状错配、样本不对），但**模式是同一个：
> 验收者≠使用者在同一条件下验证**。
> 本协议是硬红线：违反即视为虚假汇报，比不做更严重。

## 0. 一句话原则

**「做到了」的唯一判据：在使用者将会使用的同一环境、同一身份、同一数据形状下，操作一遍并拿到预期结果。除此之外的一切陈述都只是「我做了」，不是「做到了」。**

## 1. 四层验证阶梯（缺一层就少一层保证）

| 层 | 验什么 | 谁验 | 能抓什么 |
|---|---|---|---|
| L1 静态 | 代码存在、语法过、类型过 | Agent 自查 | 拼错、漏文件 |
| L2 单测/契约 | 零件按规格工作（mock/预设数据） | Agent 自查+主模型抽查 | 逻辑错 |
| L3 集成 | 真实组件组装后链路通（真 DB、真 HTTP、真身份） | 主模型**独立重跑** | 装配错、环境差异 |
| L4 用户仿真 | **零状态新用户**在目标环境走完整用户旅程 | 主模型或独立验收 Agent（禁用实施者身份） | 形状错配、权限缺口、数据形状差异 |

**只有 L4 过了才允许对用户说「修好了/做到了」。** L1-L3 全绿不构成对用户承诺的资格——两天里 4 起事故全部是 L1-L3 绿而 L4 缺失。

## 2. 报告纪律（杜绝虚报）

- 「完成」必须附**验证证据**：命令+实际输出关键行（不是转述）
- 子代理报 DONE 时，主模型必须抽查：文件存在？验收命令重跑？响应形状比对？
- 主模型自己的改动同样适用：自己说过「验证过」的，事后抽查一次（自查也会自欺）
- **禁止的措辞**：「应该可以了」「理论上没问题」「逻辑上是对的」——这些是「我猜」，不是「我验」

## 3. 身份纪律（L4 的关键）

- 验收一律用**目标用户将拥有的真实身份**：新注册账号、新激活码、真实供应商 key 形状
- 禁止用 admin/测试预置账号冒充用户验收（admin 有特权，掩盖权限缺口——writer 角色事故即此）
- 客户端模式/服务器模式/打包版/开发版，验收身份与目标环境必须一一对应

## 4. 数据形状纪律

- 跨端契约（后端→前端、服务→客户端镜像）**必须逐字段比对实际响应体**，不接受「类型定义写了」
- 用真实形状数据验收（真实 .docx 大小、真实 key 格式、真实供应商响应），不用 6 字节玩具样本
- 新增列/新增键时，同时检查：回填清单、镜像路径、响应构造、类型定义（四处联动，漏一处就是生产事故——users.storage 与 license.code 两次事故同源）

## 5. 环境变更纪律（部署类操作）

- 每次部署后立即执行 health+关键链探针，**版本号必须出现在响应里**才叫部署成功
- 写入/删除共享配置文件（.env 等）前先查「谁在引用它」（systemd/docker/env_file）
- 重建链必须显式包含每个工件的重跑（PyInstaller 会被静默跳过——0.3.9 事故），完成后核对各工件时间戳

## 6. 事故复盘模板（每次事故后 24h 内入 ADR）

1. 声称了什么？证据是什么？
2. 实际差在哪？谁发现的（用户/测试/自查）？
3. 为什么 L1-L3 没拦住？缺的是哪一层？
4. 本协议要补哪一条？

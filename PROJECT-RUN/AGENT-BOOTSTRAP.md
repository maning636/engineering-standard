# Agent 项目启动指令（完整版）

> **定位**：库根 `START-HERE.md` 是路由表（第一跳）；本文件是「新项目开工」的完整契约。
> 适用：把一份需求交给 Agent，要求它**先出计划、后执行**。
> **用法**：把顶部变量表里的 `{{...}}` 替换成实际值，然后把整份文件交给 Agent。
> 分两段执行：**第一段只出计划**（你审），**第二段按计划执行**。
> 这份文件是"给机器读"的契约，不是教材；原理去标准库看。

## 1. 你（Agent）的身份与边界

你是 `{{项目名}}` 的执行 Agent。本轮**只做计划，不改代码、不装依赖、不提交**。
项目是个人/小团队（`{{团队规模}}` 人）的 `{{项目类型}}` 项目，目标是一次性工程注入，
**不做部署**（除非项目本身有服务端；有服务端才启用部署裸仓，见标准库 Git 规范 §1）。

## 2. 输入预处理（有本地工具链时使用）

> 本节是**可选**能力：项目若有本地离线工具（OCR / 格式转换 / 解析器），
> 用它先把非文本输入转成文本，再进入需求分析——可省模型 token、且结果可复现。
> 没有这类工具就跳过本节，直接读需求文档。

**登记格式**（把 `{{本地工具链}}` 展开成下面这张表，没有就写「无」）：

| 输入类型 | 做法 | 备注 |
| --- | --- | --- |
| PDF / 图片 | 本地 OCR → 文本（JSON 含坐标与置信度） | 大文件分段处理 |
| Word / Excel | 本地转文本（pandoc / LibreOffice / 对应库） | OCR 通常不支持 Office 文档 |
| 纯文本 / Markdown | 直接读取 | 无需转换 |

**硬规则**（有工具链时适用）：

1. 工具退出码非 0 时先读 stderr，再判断；不要只看 stdout。
2. 低置信度内容必须在产出里标注「识别置信度低」，不得当成确定事实。
3. **不要编造提取结果**，只用工具输出里的原文。
4. 输出加可复现参数（如 schema 版本），不要解析 help 文本。
5. **模型不承担 OCR/转写**；工具无法处理时才允许退回模型方案，且必须先说明原因、
   写入「待拍板」，等人确认，不能静默切换。
6. 提取产物放 `{{输入目录}}`；原文件路径、命令、页数/字符数、低置信度清单、
   失败文件都要写进计划的「输入预处理」里程碑。

## 4. 工作方式与优先级（防两套流程打架）

**优先级**：仓库纪律（AGENT.md / CI）> superpowers > 个人偏好。

按 superpowers 的 `brainstorming → writing-plans` 组织思路，但：

- superpowers 的 plan 是**工作草稿**；仓库状态只认 `PROGRESS.md`。
- 架构取舍落 `docs/architecture/decisions/`（ADR：为什么 + 否掉了什么 + 代价）。
- TDD 的红→绿用于代码；**文档/配置/模板类改动不强行造测试**，在计划里写明例外。
- 评审结论落 `docs/dev-reports/`；Critical/High 必须在本轮修复。
- 完成前跑标准库的本地四步（或本项目等价命令），不写"看起来正常"。

## 5. 第一段：输出计划（只出计划）

保存到 `docs/plans/{{日期}}-initial-plan.md`，必须包含以下八节：

### A. 输入预处理报告
文件清单、每份的页数/字符数、低置信度段落、失败项与处理方式。

### B. 需求理解与歧义清单
≤10 条歧义，每条给出「建议答案 + 理由」。**不要自行假设后直接开做。**

### C. 工程注入清单
逐项列出要创建/修改的文件（AGENT.md、PROGRESS.md、.gitignore、.gitattributes、
LICENSE、CHANGELOG、ci.yml…），每项写「为什么需要」，并标注：

- **个人必做**
- **两人触发**
- **暂缓（写清触发条件）**

### D. 开发路径（按里程碑）
每个里程碑写三件事：**产出 / 验收命令 / 完成标志**。
验收命令必须是本机可直接执行的，不允许"手动确认一下"。

### E. 质量门禁
最小硬门集合（建议：lint + typecheck + test + deps-gate；Node 项目可参考
`npm run verify`），以及：

- TDD 适用范围
- 例外（文档/配置）
- CI 与本地命令的对应关系

### F. 待拍板清单
需要我决定的事：技术选型、协议、部署方式、是否公开、成本预算。
**不要替我做决定**；每条给 2–3 个选项与推荐。

### G. 明确不做什么
三远程、自动发版、PR 保护、CODEOWNERS、软著、验收表三件套等企业项，
逐项写「暂缓 + 触发条件」。

### H. 计划自检（对照 30 项检查单）
用表格标注每一项：**适用 / 不适用（写原因）/ 触发条件**。
不要为了"全套"把不适用的项硬塞进来。

**计划输出后停下，等我确认。不要顺手开始写代码。**

---

## 6. 第二段：执行计划（计划确认后）

> 计划已确认。按 `PROGRESS.md` 的阶段执行：

1. 每个里程碑开始前，把任务写进 `PROGRESS.md`「任务栈」。
2. 每个里程碑结束：跑该里程碑的验收命令 → 更新 PROGRESS → 显式列路径提交。
3. 提交纪律：
   - `git add <显式路径>`，**禁 `git add -A` / `git add .`**
   - message：`type(scope): 描述`；AI 主导的提交末行 `AI-Model: <模型名>`
   - 禁 `git stash` / `reset --hard` / `checkout .` / `clean` / `push --force`
4. 计划未覆盖的情况：写 `BLOCKED: <问题>` 到 PROGRESS 等我，**不要自由发挥**。
5. 全部里程碑完成：跑最终四门 + 更新 dev-report；未通过不得声称完成。

## 7. 本地工具链配置示例（以 OCR 为例，可整节替换）

> 若项目使用本地 OCR，按下表登记命令与退出码；不用 OCR 就删掉本节。

```bash
<ocr> --version                          # 版本自检
<ocr> --format text <图片>               # 只要全文
<ocr> --format json <图片>               # 文字 + 坐标 + 置信度
<ocr> --format jsonl <file>.pdf --schema-version 1   # 整份 PDF，流式
```

| 退出码 | 含义 |
| ---: | --- |
| 0 | 成功 |
| 64 | 用法错误 |
| 65 | 参数非法 |
| 66 | 输入文件无效 |

登记要求：写清「工具名 + 版本 + 官方文档地址 + 是否运行期联网」，
让下一个人能复现你的提取结果。

## 8. superpowers ↔ 仓库纪律映射

| superpowers | 落到仓库里的位置 |
| --- | --- |
| brainstorming | 结论进 PROGRESS 任务栈；架构取舍落 ADR |
| writing-plans | plan 文件是草稿；执行按 PROGRESS 的 P2 |
| TDD | 代码改动先红后绿；文档/配置豁免 |
| requesting-code-review | 评审结论落 `docs/dev-reports/`；Critical/High 本轮修 |
| verification-before-completion | 对应本项目的四门（lint/typecheck/test/deps-gate） |

**冲突处理**：superpowers 技能与 AGENT.md 冲突时，以 AGENT.md 为准；
它的 plan/progress 目录不作为仓库状态源。

## 9. 个人 / 两人项目的注入范围

| 项 | 个人（1 人） | 两人 | 暂缓到何时 |
| --- | --- | --- | --- |
| `.gitignore` / `.gitattributes` / LICENSE | 必做 | 必做 | — |
| AGENT.md / PROGRESS.md | 必做 | 必做 | — |
| CI（lint + test） | 必做 | 必做 | — |
| deps-gate | 建议 | 必做 | — |
| PR 流程 + 分支保护 | 不做 | 必做（1 approval） | 第二个人加入 |
| CODEOWNERS | 不做 | 必做 | 第二个人加入 |
| 部署裸仓（deploy-remote） | 不做 | 视服务端 | 项目有服务端且 GitHub 不可达 |
| release.yml 自动发版 | 不做 | 视对外发版 | 需要对外分发/自动更新 |
| 软著 SOP / 验收表三件套 | 不做 | 不做 | 有商业/合规/多人验收需求 |
| 决策台账（ADR） | 关键决策才写 | 关键决策才写 | — |
| 坑清单 | 必做（边踩边记） | 必做 | — |
| dev-reports | 按里程碑写 | 按里程碑写 | — |

## 10. 完成定义（DoD）

一个里程碑算完成，必须同时满足：

- [ ] 该里程碑的验收命令通过（贴输出，不贴形容词）
- [ ] `PROGRESS.md` 已更新（阶段 / 任务 / 遗留）
- [ ] 涉及架构取舍的，ADR 已写（为什么 + 否掉了什么 + 代价）
- [ ] 提交显式列路径、带 `AI-Model` trailer
- [ ] 没有把运行时数据 / 密钥 / 本机绝对路径带进仓库
- [ ] 文档与代码同步（口径类文档改过就更新）

项目整体算完成，还必须：

- [ ] 本地四门全绿（或本项目等价门禁）
- [ ] 30 项检查单已逐项标注（适用/不适用/触发）
- [ ] 首个 tag 与版本号单一真源一致
- [ ] 发布产物可安装、可启动（如果本轮涉及打包）

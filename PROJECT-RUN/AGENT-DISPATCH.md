# AGENT-DISPATCH · 小模型子智能体派发规范

> 适用于「主模型规划 + 小模型执行」的分工场景。  
> 版本：v1.0｜2026-10-28｜来源：多次真实的派发失败与修复经验

---

## 0. 一句话原则

**主模型负责「想清楚并验收」，小模型负责「照做并交证据」。**

派发质量的上限 = 提示词的确定性。小模型不缺写代码的手，缺的是判断力：  
你把「做什么」留空，它就会自己发明「怎么做」；你给的每个参数都写死，它就一次做对。

**判断标准**：如果你的提示词交给一个没有上下文的新人，他能不看代码库就执行完 —— 那才叫合格。

---

## 1. 判定：什么时候按「小模型」对待

满足任意两条即按本规范派发：

- 参数量明显小于主模型，或没有长链推理能力
- 有反复「自由发挥」的历史（自行改设计、加需求、改接口）
- 上下文窗口有限，长提示词会丢后半段
- 一次任务里它需要做「选择」而非「执行」

**不适用**：需要探索代码库、需要设计取舍、需要读多个文件后下判断 —— 这类给 `explore` / `plan` 角色，或主模型自己做。

## 2. 五段式派发模板（必须齐全）

### 第 1 段 · 目标（一句话，可验证）

```
任务：<动词 + 对象 + 可验证结果>
```

- ✅ 「新建 `scripts/x.py`，跑通后退出码 0」
- ❌ 「优化一下这个模块」「把文档改好」

### 第 2 段 · 精确输入

给出**绝对路径**与**现有内容片段**，不要让它自己找：

```
文件：D:\proj\scripts\release.py
现状：第 55 行 `APP_VERSION = "0.3.0"`
参考：同目录 `check.py` 的 `def main()` 结构（附 10 行原文）
```

> 小模型的「找」多数会猜。猜错一次，整轮返工。

### 第 3 段 · 完整动作（照抄级）

**给完整代码块 / 完整命令，不给「思路」。**

```
用 Write 工具创建 `D:\proj\scripts\x.py`，内容逐字照抄下面这段
（不要改缩进、不要改字符串、不要加注释）：

```python
<完整文件内容>
```
```

修改现有文件时，**优先给完整文件内容重写**，而不是「改第 60 行」。  
小模型做局部替换极易破坏周边（缩进、引号、编码、BOM）。

### 第 4 段 · 禁止事项（红线逐条列）

```
禁止：
- 不改 <名单外的文件>
- 不跑发布脚本 / 不提交 git / 不动生产环境
- 不新增依赖
- 不「优化」未要求的代码
```

> 不写禁止 → 它会顺手重构；写了禁止 → 它只动该动的。

### 第 5 段 · 验收（可复制命令 + 期望输出）

```
跑这三条，把**实际输出**贴进报告：
1. `python -m py_compile scripts/x.py` → 期望无输出、退出码 0
2. `python scripts/x.py` → 期望打印 `OK`
3. `git status --porcelain` → 期望只出现 x.py
```

> **关键**：要求贴「实际输出」，不是「已完成」。  
> 没有输出的「完成」等于没做。

## 3. 正反例对照

| 维度 | ❌ 失败写法 | ✅ 正确写法 |
|---|---|---|
| 目标 | 「给项目加个文档检查」 | 「新建 `scripts/check_docs.py`，扫描 `docs/*.md` 中的 U+FFFD，发现即退出码 1」 |
| 输入 | 「参考现有实现」 | 「参照 `scripts/a.py:1-30` 的结构，原文如下：<片段>」 |
| 动作 | 「实现这个功能」 | 「用 Write 创建该文件，内容逐字照抄以下代码块」 |
| 边界 | （无） | 「只新建这 1 个文件；不改其他任何文件；不提交」 |
| 验收 | 「做完告诉我」 | 「跑这 2 条命令，贴输出；失败就如实报告，不要重试超过 2 次」 |

## 4. 七种典型失败与对策（真实踩过）

| # | 失败表现 | 根因 | 对策 |
|---|---|---|---|
| 1 | **事实张冠李戴**：把 A 对象的行为记到 B 对象上，且格式完美、看不出错 | 它在「补全」而非「查证」 | 要求「引用外部事实必须给出获取命令并贴输出」。例：引用 commit 号 → 必须 `git log --oneline -1 <sha>` 贴结果 |
| 2 | **自由发挥设计**：自行新增字段/端点/文件 | 目标描述留了设计空间 | 目标改为「可验证结果」，并给完整实现 |
| 3 | **局部替换破坏格式**：改一行导致文件丢 BOM、缩进错乱、引号不配对 | 局部编辑 + 编码感知弱 | 要求**整文件重写**；对 `.ps1` 等敏感文件给完整内容并注明「必须保留 UTF-8 BOM」 |
| 4 | **声称完成但没验证** | 无验收命令，或有但不强制 | 每条验收命令单独一行，要求「贴实际输出，失败也贴」 |
| 5 | **中途截断**：任务做到一半上下文耗尽 | 单任务过大 | 拆到单步可完成（≤10 分钟），一次只做一件事 |
| 6 | **幻觉路径/接口**：引用了不存在的文件、函数、行号 | 未给真实片段 | 提示词里带真实路径与真实代码片段；验收里加「该路径必须存在」 |
| 7 | **越界改动**：顺手改了无关代码或删了测试让它变绿 | 无禁止清单 + 无「不得削弱测试」红线 | 禁止清单必写：不改无关文件、不删/不弱化测试、不改 CI 让红变绿 |

## 5. 任务粒度与拆分

**一个任务 = 一个可独立验收的动作。**

- ✅ 新建 1 个文件 + 跑 2 条验证
- ✅ 改 1 处配置 + 跑 1 条验证
- ❌ 「实现整套功能并测试并提交」（应拆成 3 个任务）

**拆分信号**（出现任一即拆）：
- 提示词超过约 60 行
- 需要改 3 个以上文件
- 步骤之间需要它做判断（「如果 A 则 B」超过 1 层）

**并行规则**：任务之间**不共享文件**才并行；共享文件的必须串行，否则互相覆盖。

---

## 6. 主模型验收清单（收到结果后逐条过）

不要信「已完成」，抽查这五项：

- [ ] **文件真的存在**：`ls` / `wc -l` 看路径与大小，不看它的描述
- [ ] **关键内容真的对**：抽查它声称的 2-3 个数字/路径/引用，用独立命令复核
- [ ] **验收命令真的跑过**：让它贴实际输出，或自己重跑一次
- [ ] **没有越界改动**：`git status --porcelain` 对比预期文件清单
- [ ] **负向能力**：涉及门禁/检查类改动，必须**故意制造一次失败**验证它真能拦住

> 最后一条最容易被跳过：只测「正常通过」的门禁，等于没测门禁。

---

## 7. 上下文预算

- 指令放**最前面**，背景放后面（有些实现会截断尾部）
- 单次派发控制在 **约 60 行以内**；超了就拆
- 不要塞历史对话，只给「当前状态 + 本次要做的事」
- 需要它记住的约束，在**开头和结尾各出现一次**

---

## 8. 何时不该派给小模型

以下任务交给它，返工成本高于自己做的成本：

- 需要读 3 个以上文件才能决策（选型、定位根因）
- 需要设计接口或数据结构
- 涉及不可逆操作且无验收手段（生产部署、数据迁移）
- 需要「判断某段输出是否正确」

这些留在主模型，或交给具备推理能力的角色。

---

## 结语

小模型的价值是**廉价且并行地执行确定性动作**；  
它的风险是**在留白处自由发挥**。

派发规范的本质，就是把留白全部填掉——  
让它的每一步都只有一种正确做法，验收又都能一眼判定真假。

> 检验标准：同一份提示词发给两个不同的执行者，产出应当几乎一致。  
> 如果两份产出差异很大，说明提示词里还有留白，不是执行者的问题。

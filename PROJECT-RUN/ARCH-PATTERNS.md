# ARCH-PATTERNS · 架构模式选择

> 与 `CRAFTS/DESIGN.md` 配套：设计时先选模式，再谈实现。

## 0. 一句话

架构决定的是「以后能改多快」，不是「现在能做多少」——选错的代价总在半年后显现。

## 1. 三种部署形态

| 形态 | 数据在哪 | 优点 | 代价 |
| --- | --- | --- | --- |
| 纯本地（桌面/单机服务） | 用户机器 | 离线可用、隐私边界最清晰、无月费 | 更新分发靠人工、多端一致难、无集中遥测 |
| 纯云端（SaaS） | 厂商服务器 | 统一升级、集中运营、多端一致 | 依赖网络、用户数据出域、离线不可用 |
| **混合（本地为主 + 可选云端）** | 本地为主 | 日常离线可用，能力可按需上云 | 边界设计复杂、需维护两套路径 |

三种形态没有绝对优劣，取决于「离线可用」与「集中运营」哪个是主线。绝大多数文档类工具属于重编辑、轻协作，天然适合**混合**：把编辑这条主路径留在本地，把更新、同步、推理这类非核心能力按需上云。

混合形态的核心问题不是技术，是**承诺边界**——哪些能力必须离线可用、哪些可以联网、断网时降级到什么程度，必须写清楚，且写进产品说明而不是留在实现细节里。

判断形态时问三个问题：

1. 用户是否会在无网环境下完成核心任务？（是 → 至少要「本地为主」）
2. 是否有需要持续更新的数据？（是 → 需要可选的云端下发）
3. 是否接受把主数据放到厂商服务器？（否 → 排除纯云端）

## 2. 数据不出域承诺怎么落地

以下五条都是可验证的做法，逐条对应一条验收标准：

1. **默认存储位置在用户机器，路径可查。** 不静默改写到其他盘或隐藏目录，路径在设置页可见、可复制。
2. **除显式开启的功能外不发网络请求。** 自查方法：抓包或代理观察——清空网络列表后做一轮完整操作，除被标记「显式联网」的调用外，应看不到任何出域流量。
3. **云端调用必须显式开关 + 明确提示发送了什么。** 开关默认关；打开时告知将上传的数据类别与用途，不是一句「联网」了事。
4. **日志与遥测默认关闭或脱敏。** 即使开启，也不含文档正文、路径全名、密钥等敏感字段。
5. **隐私声明与代码行为一致。** 不一致时以代码为准——要么改文档，要么改代码，禁止让声明替代码背锅。

落地时注意两条实操细节：

- **网络出口统一收口。** 所有出域请求走同一个网关函数，审计、开关、提示都在一处生效，而不是散在各业务模块里各写各的。
- **「不发请求」要有测试守护。** 用离线环境或 mock 断言：关掉一切联网开关后，任何核心操作都不应触发网络调用，防止后续改动悄悄引入联网。

## 3. 可选云端的边界划分

| 能力 | 建议位置 | 理由 |
| --- | --- | --- |
| 核心编辑与本地解析 | 本地 | 编辑是最常用路径，必须离线可用、低延迟 |
| 需要持续更新的规则/知识/模板 | 云端下发（可缓存） | 数据会过期，需要可更新的来源，但可本地缓存兜底 |
| 大模型推理 | 用户自备密钥直连（或可选代理） | 数据不出域，且把成本与合规选择留给用户 |
| 授权与心跳 | 云端（但必须支持离线宽限） | 需要吊销能力，但不能因断网就锁死本地功能 |
| 备份/多端同步 | 云端（可选，需明确加密方式） | 跨设备价值高，但属可选功能，加密方式必须写明 |
| 遥测与统计 | 云端（默认关闭，opt-in） | 不默认收集，用户主动开启后才上报 |

每条边界都带一个「降级路径」：断网时该能力退化为本地缓存、本地单机、或直接不可用并给出明确提示。**没有降级路径的云端依赖，等于把本地主路径架在网络上。**

划分时机建议在首个云端能力立项前完成——先画这张表，再写代码；而不是等每个功能各自决定「要不要上云」，最后拼成一张互相矛盾的边界图。

## 4. 可插拔的三种粒度

- **技能/插件**——业务能力可增删，如导入器、导出器、特定行业规则包。
- **渠道/适配器**——同一能力多种实现，如多模型厂商、多存储后端、多文件格式读写。
- **渲染/模板**——输出形态可变，如不同版式、不同导出目标、不同平台的呈现。

三种粒度的共同判断标准一句话：**接口稳定、实现可替换、缺失时能降级。** 三者缺一就不算合格的插拔，只能算「可配置」。

各粒度一句话示例：

- 技能：某行业模板包缺失时，退回通用模板，不报错。
- 适配器：某模型厂商密钥未配置时，自动回退到另一厂商，或提示手动选择。
- 模板：目标渲染器不存在时，输出降级为纯文本，仍可交付。

## 5. 分层边界（禁止跨层直调）

典型四层，自上而下：UI / 路由·接口 / 引擎与服务 / 数据访问。

三条规则：

1. **UI 不得直连数据库或文件系统。** 视图只认接口，不认存储细节。
2. **路由层只做参数校验与编排，不放业务算法。** 校验通过后转交下层，不塞入计算逻辑。
3. **引擎层不依赖具体框架。** 便于单测与替换，框架耦合只出现在最外层适配处。

判断是否越层的方法——「换掉 UI 框架，引擎要不要改？」 若答案是需要改，说明引擎已被 UI 或框架污染，边界失守。

另一条自查：**数据访问层不应被业务层「借用」成工具库。** 若某处直接调数据库只为拿一个配置项，说明编排顺序错了，应把该取数上移到服务层统一完成。

## 6. 什么时候该拆服务、什么时候别拆

**该拆的 4 个信号：**

- 依赖集冲突——一个模块要几十 MB 的 native 库，拖累整体启动与体积。
- 独立伸缩需求——某块负载与其余部分完全不成比例，单独扩更划算。
- 独立发布节奏——某块需要更频繁或独立的上线节奏。
- 故障需要隔离——某块的崩溃不应拖垮整体。

**别拆的 3 个信号：**

- 共享同一份数据且强一致——拆开后一致性成本远超收益。
- 团队规模小于 3 人——运维负担吃光开发时间。
- 只是「看起来更专业」——为架构而架构，没有实际痛点。

拆分的代价是运维复杂度与调试成本，早期优先「模块化单进程」：先做好模块边界，等真实信号出现再拆。判断顺序建议自下而上——先确认「有没有一个真实痛点」，再决定「拆了能不能解决它」；没有痛点就继续单进程。

## 7. 反模式

| 反模式 | 后果 + 替代 |
| --- | --- |
| 过早微服务 | 运维压垮团队 / 模块化单进程 |
| 全局单例满天飞 | 无法测试、隐式依赖 / 依赖注入或显式传参 |
| UI 直连存储 | 无法换端、安全边界失守 / 走接口层 |
| 把授权逻辑散在各处 | 一处漏就全漏 / 集中到中间件 |
| 为「以后可能要用」提前抽象 | 无用抽象拖慢迭代 / 出现第二个使用方时再抽象 |

反模式共同点：**都是「短期顺手、长期还债」。** 评审时重点盯这几类，因为它们通常不会在功能上立刻报错，而是半年后在「要改、要测、要换」时集中爆发。

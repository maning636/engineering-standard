# ACCEPTANCE · 客户验收

> 位置：签约项目在 P2/P3 的 VERIFY 通过后、P4 正式 RELEASE 之前。需要操作候选包时，可使用未正式发布的 UAT 候选包。
> 解决的问题：VERIFY 证明“我们做对了”，ACCEPTANCE 证明“客户认可做对了”。两者不能互相替代。
> 上游：`REQUIREMENTS.md` 的需求编号和验收用例（F03-A01 这类）。下游：`RELEASE.md`，验收结论为“通过”或“有条件通过”才能上线。

## 1. 三条底线

1. **验收集先锁定，再交付。** 第一次演示之前，验收用例清单要客户书面确认（邮件或签字都算），确认后版本号写进清单头部。之后客户新增的检查项，一律走变更提案（CP），不进本轮验收。
2. **用例只从验收标准派生。** 每条 UAT 用例必须指向一条需求编号下的验收标准。没有出处的用例是新需求，不是验收用例。
3. **问题分级，签字有条件。** A 级问题清零才能签字；B 级问题可以带着签，但每条要有修复期限和责任人。

## 2. 流程

| 步骤 | 做什么 | 产出 | 谁负责 |
|---|---|---|---|
| A1 锁定 | 从 prd/REQ 的验收标准生成 UAT 用例，客户确认 | `docs/acceptance/UAT-CASES.md`（带版本号） | 我方项目负责人 |
| A2 预验 | 我方按 UAT 用例自己先跑一遍，失败的先修 | 预验记录（证据路径写进追踪表） | 开发 / Agent |
| A3 正式验收 | 客户方在约定环境里逐条执行，我方旁观记录 | 执行结果 + 问题清单 | 客户方验收人 |
| A4 处理问题 | 问题定级，A 级修完回到 A3 复验相关用例 | `docs/acceptance/PUNCH-LIST.md` | 双方 |
| A5 结论 | 出验收报告，签字 | `docs/acceptance/ACCEPTANCE-REPORT-<版本>.md` | 双方 |

预验（A2）是硬步骤：我方自己跑都不过的用例，不允许拿到客户面前。

## 3. UAT 用例怎么写

- 编号：`<需求编号短号>-A<两位>`，例如 `F03-A01`，和 REQUIREMENTS.md 的验收用例编号一致，一条验收标准至少一条用例。
- 用业务语言写：“质检员上传一张 PDF 图纸”，不写“调用 /api/upload”。
- 每条有前置条件、操作步骤、期望结果、通过判定。期望结果要能当场看出对错。
- AI 类需求（问答、生成、分类）不用单条对错判，用评估集：写清样本数、判定方式和通过线（例如“30 题里至少 27 题答对，且引用来源可点开”）。通过线必须在 A1 锁定，不能验收现场再定。
- 数据：用客户提供的或双方确认的脱敏数据，写清数据来源。

## 4. 问题分级

| 级别 | 定义 | 对签字的影响 |
|---|---|---|
| A 级 | 必须需求的核心流程走不通；数据错误或丢失；安全问题；AI 评估低于通过线 | 有一个就不能签 |
| B 级 | 功能能用但有明显缺陷，有绕行办法；应该需求未达标 | 可带条件签字，每条写修复期限和责任人 |
| C 级 | 体验、文案、样式问题；可以需求 | 不影响签字，进入后续迭代清单 |

定级有争议时，以需求的优先级为准：问题落在“必须”需求上，最低 B 级。双方仍有分歧，记录在验收报告的“争议项”里，由合同约定的负责人裁定。

新发现但不在验收集里的问题，先区分性质，不能一概标“范围外”：
- **新增能力或新增检查要求**：属于需求变化，记进问题清单并按需走 CP，不进入本轮既定范围。
- **既有功能缺陷、数据错误、安全问题或未满足既有验收标准**：即使在原验收集之外，也必须定级并纳入签字判断；A 级阻断验收，修复后补入回归用例。
锁定验收集是为了防止临时加需求，不是为了排除真实缺陷。

## 5. 结论三选一

- **通过**：A 级 0，B 级 0。
- **有条件通过**：A 级 0，B 级都有期限和责任人。期限到了没修完，按合同处理，不自动作废结论。
- **不通过**：存在 A 级问题。修复后只复验受影响的用例和冒烟用例，不必全量重跑，复验范围写进报告。

## 6. 和付款、合同的关系

- 验收报告是付款节点的凭证。哪个结论对应哪笔款，写在合同里，这里只引用，不另立规则。
- 合同里如果有“交付后 N 天内未提出异议视为验收通过”这类默认验收条款，在验收报告里写明起算日期。本规范不替合同定条款，只要求把条款原文贴进报告附录。
- 验收报告和 UAT 用例的版本号要对上。签字时用的用例版本，就是交付范围的最终依据。

## 7. 和其他文件的关系

- `REQUIREMENTS.md`：用例来源；验收后把结论回填进追踪表“验收结论”列，再跑 `trace-check.mjs --stage release`。
- `VERIFY.md`：VERIFY 通过是进入 A2 预验的前提。
- `RELEASE.md`：结论为通过或有条件通过才能上线；有条件通过时，B 级清单要随发布记录一起归档。
- 模板：`templates/UAT-CASES-TEMPLATE.md`、`templates/PUNCH-LIST-TEMPLATE.md`、`templates/ACCEPTANCE-REPORT-TEMPLATE.md`。

## 8. 借鉴边界

借鉴了软件工程里 UAT（用户验收测试）和工程行业“尾项清单”（punch list）的做法。没有照搬 IEEE 829 的完整测试文档体系，小团队用不上那么多文档。法律效力相关的内容以合同为准，这里不提供法律意见。

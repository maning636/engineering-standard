# DESIGN · 设计先行

> 工艺层第 1 篇。上游：`AGENT-PROTOCOL.md` P2；产出落 `docs/architecture/decisions/`。

## 0. 一句话
**先想清楚再写代码——没有 spec 和验收标准的需求，不允许直接开工。**

## 1. 什么时候必须走设计

出现下面任一信号，先出设计，再动代码。

| 信号 | 说明 | 需要的产出 |
| --- | --- | --- |
| 改动跨 3 个以上模块 | 影响面大，牵一发动全身 | spec + ADR |
| 涉及数据模型/接口契约变化 | 数据结构或接口签名变更，波及调用方 | spec + 迁移方案 |
| 有多种可行技术路线 | 无法一眼判断优劣，各有取舍 | 方案对比表 |
| 不可逆或难回滚 | 上线后修改代价高，甚至无法回头 | spec + 回滚方案 |
| 需求本身有歧义 | 解读存在多种可能，理解会分叉 | 歧义清单（先问，不猜） |

## 2. Spec 最小结构

```markdown
# <需求名> Spec

### 目标
一句话，可验证：做完后能用什么命令/操作确认达成。

### 非目标
明确不做什么，防止范围蔓延。例：本版本不做权限细分，沿用现有角色。

### 验收标准
每条都能用命令或操作验证：
- [ ] 例：`GET /projects/{id}` 返回 200 且 body 含 `name`
- [ ] 例：并发 10 用户同时提交，无重复记录

### 约束
兼容性/性能/安全/合规红线。例：接口向后兼容 v1；P99 < 300ms；敏感字段不入日志。

### 风险与未知
列出来，不假装没有。例：第三方回调超时行为未知，需联调验证。
```

## 3. 方案对比（至少两个）

只有一个方案等于没有选择。至少两个，且被否掉的方案必须写「为什么否」，否则将来会有人重新提。

| 方案 | 优点 | 代价 | 结论（选它/否掉它的理由） |
| --- | --- | --- | --- |
| 方案 A：xxx | ... | ... | 选它：... |
| 方案 B：yyy | ... | ... | 否掉：为什么否 |

**填表示例（缓存选型）：**

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| A：进程内缓存 | 最快、无网络开销 | 多实例不一致、重启丢失 | 选它：单实例读多写少 |
| B：集中式缓存 | 多实例一致、可扩容 | 引入依赖、网络往返 | 否掉：当前单实例用不上，且多一个故障点 |

## 4. ADR 何时写、写什么

触发条件（满足其一）：

- 架构边界：模块划分、依赖方向、分层方式
- 技术选型：语言/框架/库/中间件取舍
- 协议与契约：接口、消息、数据格式约定
- 版本与发布策略：兼容策略、发布节奏
- 门禁规则变更：CI/评审/审批规则调整

必含 4 要素：

- 为什么（背景）：当时的约束、上下文
- 决定了什么：选定的方案
- 否掉了什么及原因：落选方案 + 理由
- 代价：引入的成本、权衡、后续义务

证据分级：

- 【已验证】跑过：本地/CI 实测通过
- 【已确认】查过文档或事实：官方文档、可查证事实
- 【推测】尚未验证：基于推理，需后续确认

一句话：三个月后的你会感谢现在写了「为什么」。

## 5. 设计评审看什么

- 验收标准是否可执行：不是「体验好」这类主观词，要能跑命令或操作验证
- 是否覆盖失败路径：超时/重试/部分失败/权限不足都要有处理
- 数据与隐私边界是否清楚：存哪、传哪、谁能看
- 可回滚性：出问题能否降级或撤回
- 与现有约定是否冲突：命名/错误码/协议

## 6. 反模式

| 反模式 | 后果 + 替代做法 |
| --- | --- |
| 直接开写 | 返工 / 先写 spec |
| 边写边想 | 结构漂移 / 先定边界 |
| 只设计 happy path | 上线即出事 / 补失败路径 |
| 方案只写一个 | 无对比 / 至少两个 |
| 决策只记结论不记理由 | 后人无法判断能否推翻 / 写 ADR |
| 把「以后再优化」当设计 | 技术债 / 写进非目标或待办，明确触发条件 |

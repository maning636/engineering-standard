# EVAL · AI 功能效果评估

> 位置：FLOW 的 P2（开发）到 P5（上线）全程。AI 功能的“测试”就是评估集，评估集不过，功能不算完成。
> 解决的问题：AI 输出没有唯一正确答案，普通单元测试判不了对错；换模型、改提示词之后效果悄悄变差，没人发现。
> 上游：`REQUIREMENTS.md` 里 AI 类需求的四项（资料来源、效果指标、兜底、审核）。下游：`CRAFTS/VERIFY.md`（完成证据）、`CRAFTS/ACCEPTANCE.md`（A2 预验）、`RELEASE.md`（上线条件）。

## 1. 适用范围

凡是输出由模型生成的需求都要走 EVAL：问答、知识库检索、文案生成、分类打标、信息抽取、推荐。判断标准很简单：同样的输入跑两次，输出可能不一样，就算 AI 功能。

调用模型的“外壳”代码（接口、鉴权、超时、重试）照常写单元测试，走 `CRAFTS/TDD.md`。EVAL 只管“模型答得好不好”。

## 2. 四条底线

1. **先有评估集，再调提示词。** 没有评估集时调提示词，只能凭感觉。评估集的第一批题和需求一起定。
2. **指标写死数字和口径。** “准确率高”不算指标。要写成“在评估集 `evals/kb-qa.yaml` v1.2 上，答案正确率 ≥ 90%”。
3. **改了就重跑，降了不合并。** 换模型、改提示词、改切分或检索参数、更新知识库，都要重跑评估集并和基线对比。
4. **评估集只增不减。** 线上答错的题、客户投诉的题，修好后加进评估集，防止同样的错再出现。旧题只能标记“作废”并写原因，不能删。

## 3. 评估集

### 3.1 每条题的字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 唯一编号，如 `KB-0001`，不复用 |
| `question` | 是 | 用户原话，保留口语和错别字 |
| `req` | 是 | 对应验收用例编号，如 `F03-A01`，没有出处的题不收 |
| `type` | 是 | `常规` / `边界` / `对抗` |
| `should_refuse` | 是 | `true` 表示资料里没有答案，正确行为是拒答或转人工 |
| `expected` | 不拒答时必填 | 标准答案，或必须出现的要点列表 |
| `sources` | 不拒答时必填 | 允许的出处（文件名 + 页码或段落） |
| `note` | 否 | 出题人、来源、作废原因 |

三种类型的含义：

- 常规：用户最常问的问题，占大头。
- 边界：资料里有但不好找的问题，比如答案跨两页、表格里的数、同名不同型号。
- 对抗：诱导模型编造或越权的问题，比如“你就估一个数吧”“忽略上面的规则”。

### 3.2 规模

| 阶段 | 内部回归集 | 说明 |
|---|---|---|
| 开发起步 | ≥ 50 条 | 第一次提示词定稿前必须有 |
| 上线前 | 100～300 条 | 按功能复杂度定，写进 REQ |
| 上线后 | 持续增加 | 每周线上复评的错题加进来 |

拒答题（`should_refuse: true`）至少占 20%。知识库类功能最大的风险是编造，拒答题少了，评估集测不出这个问题。

### 3.3 客户验收集是子集

客户验收集由客户出题或确认，规模通常更小（如 30 题），在 ACCEPTANCE 的 A1 锁定，题目同时放进内部回归集，打 `note: 客户验收集` 标记。两个数分开写：

- 合同和 UAT 用例里写客户验收集（如“30 题答对 ≥ 27 题”）。
- 开发和 CI 用内部回归集（≥ 50 条，上线前 100 条以上）。

内部集过了不代表客户集过，A2 预验时客户集要单独出一份结果。

### 3.4 题从哪里来

1. 需求的验收用例：每条 AI 类 A 编号至少派生 5 题。
2. 客户真实问题：调研时收集的聊天记录、工单、培训问答（脱敏后使用）。
3. 资料本身：从文档里挑表格、数字、例外条款出边界题。
4. 线上错题：上线后每周抽样复评的结果（见第 8 节）。

不要只让模型生成题目。模型出的题偏简单、偏书面，测不出真实用户的问法。模型出题最多占 30%，并且要人工逐条审过。

## 4. 判分三层

| 层 | 做法 | 用在哪 | 成本 |
|---|---|---|---|
| 规则判分 | 包含关键词、正则匹配出处格式、拒答话术、JSON 格式、延迟、成本 | 每次提交，进 CI | 几乎为零 |
| 模型判分 | 另一个模型按评分表打分（答案是否和标准一致、有没有编造） | 改提示词、换模型、发版前 | 按调用计费 |
| 人工抽检 | 每版抽 10%～20%，对照标准答案人工判 | 发版前、模型判分结果可疑时 | 人工时间 |

要求：

- 能用规则判的不用模型判。数字、型号、页码这类答案，用包含或正则判就够了。
- 模型判分的评分表写进评估集说明（`EVAL-SET-TEMPLATE.md` 第 3 节），评审模型和被测模型不用同一个。
- 人工抽检的结果用来校准模型判分：人工和模型判定不一致超过 10%，先改评分表，再信模型判分。
- 中文评分要给评审模型中文的评分提示，不能直接用工具默认的英文提示。

关键词包含、出处字符串和拒答话术只是**规则代理指标**：它们能证明格式或关键词符合预期，不能单独证明语义正确、出处支持答案或回答没有编造。
高风险业务必须用语义评审和人工抽检校准这些代理指标；不能用总准确率掩盖关键项漏报。

## 5. 指标与阈值

至少四项，知识库类再加一项：

| 指标名（统一叫法） | 含义 | 常见阈值 |
|---|---|---|
| `answer_correct` | 不拒答题中，答案正确的比例 | ≥ 90% |
| `citation_correct` | 不拒答题中，给出的出处在允许范围内的比例 | ≥ 95% |
| `refusal_correct` | 拒答题中，正确拒答（没编造）的比例 | ≥ 95% |
| `latency` | 单题响应时间达标的比例（如 ≤ 10 秒） | ≥ 95% |
| `cost` | 单题成本达标的比例（按需） | 按预算定 |
| `retrieval_hit`（知识库类） | 检索结果里包含正确出处的比例 | ≥ 90% |
| `critical_recall`（高风险业务可选） | 关键条款/关键事实被正确找出的比例，单独成组 | 按损失定，通常高于总准确率 |
| `critical_false_negative`（高风险业务可选） | 关键项被漏报的比例，专门看代价最高的错误 | 按业务风险约定 |

指标名在评估配置、summary.json、规则文件、报告里保持一致，脚本按名字对比。关键项指标需要独立标签和判定规则，不能用普通题的平均分代替。

阈值写进 REQ 的效果指标一栏，口径固定为“在评估集 X 版本 Y 上，指标 Z ≥ N”。阈值来自客户口径时，以客户为准；客户没给时，用上表并在需求确认时让客户认可。

## 6. 兜底行为必须有题

REQUIREMENTS 里 AI 需求的“兜底”一项（查不到怎么回、什么情况转人工），每一条都要有对应的拒答题或对抗题。例如兜底写了“查不到回答‘未在 SOP 中找到’并提示联系王工”，评估集里就要有资料里确实没有的题，判分规则检查回答里有“未在 SOP 中找到”且没有编造的数字。

兜底没有对应题，`eval-check lint` 不会报错，但追踪表的这一行不能标“已验证”。

## 7. 回归基线

- 每次发版，把当次评估结果存为基线：`evals/baselines/<集名>-<版本>.json`。
- 以下任一变化都要重跑评估集，并用 `eval-check check --baseline` 对比：
  - 换模型或模型版本；
  - 改系统提示词、少样本示例；
  - 改文档切分、向量模型、检索参数（top-k、重排）；
  - 知识库批量更新（新增或替换资料超过 10%）。
- 任一关键指标比基线下降超过阈值（默认 2 个百分点，写在规则文件 `max_drop_pp`），合并门不通过。确实要接受下降的（比如换便宜模型），走变更提案 CP，写明下降多少、换来什么，客户同意后更新基线。
- CI 里每次提交跑规则判分；模型判分在合并到主干前跑一次，不必每次提交都跑。
- 每次 `summarize --set` 必须记录 `eval_set_hash`（题库内容的 SHA-256）。基线哈希不同，说明同名题库内容已变化，不能直接比较分数。
- 重复 ID、集合外 ID 进入 `errors`；缺题进入 `missing`；`check` 对任一非空错误集合返回 1。旧基线没有哈希时只提示兼容，新基线必须补齐。

## 8. 线上复评

- 上线后每周从真实对话里抽样（建议 50 条或 5%，取大者），人工判对错。
- 答错的题：定位原因（资料缺失、检索没找到、模型编造），修复后加进评估集，`note` 写来源日期。
- 复评正确率低于上线时评估结果 5 个百分点以上，按 B 级问题处理，进问题清单。
- 线上日志和抽样工具属于运维监控（G5），EVAL 只接收复评产出的错题。

## 9. 证据衔接

| 环节 | 要求 |
|---|---|
| VERIFY | AI 功能的完成证据必须包括：评估报告（`EVAL-REPORT-TEMPLATE.md`）和 `eval-check check` 退出码 0 的输出 |
| 追踪表 | AI 类验收用例的“证据”列填评估配置和用例编号，如 `evals/kb-qa.yaml; F03-A01, F03-A02` |
| ACCEPTANCE A2 | 预验时客户验收集单独跑一份报告，低于通过线不能进 A3 |
| RELEASE | 评估达标、基线已存档，才能上线 |

## 10. 合同口径

- 合同里写准确率，必须同时写明评估集名称、版本、题数和判定方式。例如：“在双方确认的评估集 kb-qa v1.0（30 题）上，答案正确率不低于 90%”。
- 不承诺“所有问题都能答对”，不承诺资料范围以外的问题。
- 写明资料更新的责任方：客户资料变了没通知，导致答错，不算我方缺陷。
- 评估集的所有权和保密要求写进合同，评估集里含客户数据时按客户数据处理。

## 附录 A · 工具分层（可替换）

规范只认第 B 节的 summary.json 格式，工具可以换。目前推荐的组合：

| 用途 | 推荐 | 说明 |
|---|---|---|
| 评估集运行、断言、回归 | promptfoo（MIT，Node） | YAML 配置，规则判分和模型判分都有，能进 CI |
| 知识库检索细分指标 | promptfoo 自带的上下文断言；不够再选 ragas 或 deepeval 之一 | 不要两个都上，指标口径会打架 |
| 线上日志与抽样复评 | langfuse 等，归 G5 | 不进 EVAL |

promptfoo 常用断言和本规范指标的对应：

| 指标 | 断言写法 |
|---|---|
| `answer_correct` | `contains-all` / `icontains` 判要点；要点难以穷举时用 `llm-rubric` 或 `factuality`，配中文 `rubricPrompt` |
| `citation_correct` | `regex` 判出处格式和页码，如 `SOP-CNC-04.*第\s*17\s*页` |
| `refusal_correct` | `icontains` 判拒答话术，加 `not-regex` 判没有编造数字 |
| `latency` | `latency`，阈值单位是毫秒 |
| `cost` | `cost` |
| `retrieval_hit` | `context-recall` / `context-relevance`，需要把检索结果放进 `vars.context` 或用 `contextTransform` 取出 |

每条断言都写 `metric: <指标名>`，`eval-check summarize` 按它聚合；没写 metric 的断言按断言类型名聚合。

## 附录 B · 统一结果格式 summary.json

```json
{
  "eval_set": "kb-qa",
  "eval_set_hash": "<题库内容的 SHA-256>",
  "version": "v1.2",
  "model": "被测模型名",
  "prompt_version": "p-2026-11-03",
  "cases": 120,
  "errors": 0,
  "error_details": [],
  "missing": [],
  "metrics": {
    "answer_correct": { "pass": 85, "total": 92, "rate": 0.9239 },
    "refusal_correct": { "pass": 27, "total": 28, "rate": 0.9643 }
  }
}
```

规则文件 `<集名>.rules.json`：

```json
{
  "min_cases": 50,
  "max_drop_pp": 2,
  "metrics": {
    "answer_correct": { "min": 0.90 },
    "citation_correct": { "min": 0.95 },
    "refusal_correct": { "min": 0.95 },
    "latency": { "min": 0.95 }
  }
}
```

脚本 `scripts/orchestrate/eval-check.mjs`：

```bash
node scripts/orchestrate/eval-check.mjs lint evals/kb-qa.jsonl --min 50
node scripts/orchestrate/eval-check.mjs export evals/kb-qa.jsonl --out evals/kb-qa.tests.jsonl --refusal "未在 SOP 中找到"
npx promptfoo@<固定版本> eval -c evals/kb-qa.yaml --output results.jsonl
node scripts/orchestrate/eval-check.mjs summarize results.jsonl --set evals/kb-qa.jsonl --out summary.json
node scripts/orchestrate/eval-check.mjs check summary.json --rules evals/kb-qa.rules.json --baseline evals/baselines/kb-qa-v1.1.json
```

退出码：0 通过，1 不达标，2 用法或文件错误。换用别的评估工具时，只要产出同样格式的 summary.json，`check` 照常可用。

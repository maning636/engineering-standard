# REVIEW · 变更评审

> 工艺层第 3 篇。上游：`AGENT-PROTOCOL.md` P3；配套：`AGENT-DISPATCH.md`（子智能体产出评审）。

## 0. 一句话
评审是找问题，不是走过场——「看起来不错」不是评审结论。评审的价值在于把隐藏的问题在合并前暴露出来，而不是给改动盖一个通过章。凡是只写「LGTM」、没有指出任何具体问题、没有对照验收标准的评审，都应当视为未完成。

## 分级处置表

| 级别 | 定义 | 处置 | 是否阻断合并 |
| --- | --- | --- | --- |
| Critical | 数据丢失 / 凭据泄露 / 门禁被绕过 / 生产中断 | 立即回退或修复 | 是 |
| High | 破坏兼容 / 性能明显回退 / 关键路径缺测试 / 明显的错误处理缺失 | 本 PR 内修 | 是 |
| Medium | 设计漂移 / 文档未同步 / 命名不一致 / 可维护性下降 | 本 PR 或下一个 | 否 |
| Low | 措辞 / 格式 / 注释 | 记录到待办 | 否 |

分级要按**后果**判，不是按改动行数判。一个三行的改动可能因绕过门禁而升级为 Critical；一个五百行的重构若行为不变、测试齐全，也可能只是 Medium。行数是线索不是标准，真正决定级别的是「如果带着这个问题上线，会发生什么」。

各档处置的边界：

- Critical 与 High 都阻断合并，区别在于可否在本 PR 内收尾：Critical 要求立即回退或当场修复，High 允许在本 PR 内修复后合并。
- Medium 不阻断合并，但必须在「本 PR 或下一个 PR」内解决，不能无限期挂起。
- Low 记录到待办清单即可，随下次相关改动顺手处理。

评审结论必须落到某一个级别上。写「整体看起来还行」「建议慎重」这类含糊结论，等于没有分级，等于没给出可执行的决策。

定级时的判断顺序：

- 先对照 Critical 的定义逐项核验：是否可能造成数据丢失、凭据泄露、门禁被绕过、生产中断。命中任何一项，直接定为 Critical，不再往下看。
- 未命中 Critical，再对照 High：是否破坏兼容、性能明显回退、关键路径缺测试、错误处理明显缺失。命中则定为 High。
- 都不命中，再评估维护性影响，落到 Medium；只涉及措辞、格式、注释，落到 Low。

## 评审者需要什么输入

- 明确的 diff 范围（base..head SHA）
- 这次改动的目标与验收标准（没有就要求补齐）
- 涉及的红线与约定（避免用错标准）
- 已知的取舍与豁免（作者应主动说明）
- 相关背景文档索引（而不是让评审者猜）

输入不全时先要输入再评审，不要凭猜测打分。评审者不是侦探，没有 diff 范围就无从判断改动是否越界；没有验收标准就无从判断改动是否达标；不知道红线与约定，就容易用错标准，把合规的改动误判为问题，或放过真正的违规。

作者应在发起评审时就主动给出取舍与豁免，而不是等评审者质疑后才补。已经做过的取舍（例如为了兼容暂不修某处、某个已知边界暂不处理）写清楚，能避免评审者重复提出已决策的问题。

## 评审怎么读（两遍法）

- 第一遍看结构：改动范围是否合理、是否夹带无关修改、抽象层次是否一致
- 第二遍看细节：边界条件、错误处理、并发/时序、资源释放、日志与敏感信息

第一遍是过滤，第二遍才是找问题。先读 diff 全貌，确认改的是该改的；再逐行抠细节。顺序反过来容易陷进局部细节，失去对整体意图的判断。

细节检查清单（第二遍逐项过）：

- 边界条件：空输入、超长输入、最小/最大值、空集合、首尾元素、并发临界
- 错误处理：异常是否被捕获、失败路径是否有返回值、用户是否看到可理解的信息
- 并发与时序：共享状态是否加锁、操作是否原子、是否存在检查-使用之间的竞态
- 资源释放：文件句柄、连接、锁、临时文件、订阅/监听是否在退出路径上关闭
- 日志与敏感信息：日志是否打印凭据、token、个人数据；错误堆栈是否泄漏内部路径

超过 ~400 行的 diff 应拆批评审，一次看不完的评审等于没做。评审者注意力有限，一次硬啃大 diff 只会漏掉后半段的问题。要么请作者拆分提交，要么分多轮、按文件或按逻辑块分批看完再汇总。

两遍都读完，对没有问题的部分也要在总结里说明「已核验」，不要让作者猜哪些看过了。没看的部分明确标出「未覆盖」，避免把未看的部分当成默认通过。

## 反馈怎么写

每条反馈必须包含三要素：位置（文件:行）/ 问题是什么 / 为什么重要 + 建议怎么改。

- **位置**：`文件:行`，定位到具体行，不用「某处」「相关代码」这类模糊指向。
- **问题**：描述现象与触发条件，说明什么情况下会出错，而不是只给结论。
- **为什么重要 + 建议**：说明影响的严重性（对应到分级表），并给出可执行的改法，必要时附上预期测试。

反例（只给结论、不给证据和改法）：

```
这里有问题
建议优化一下
```

正例（有位置、有触发条件、有影响、有改法）：

```
`src/x.py:42` 未校验空输入，传入空串会走到 500；
建议在此处返回 400 并补一条测试。
```

区分「必须改」与「建议」，不要让建议看起来像阻断项。反馈要明确标注是阻断性的「必须改」，还是非阻断性的「建议」；把建议写进 Critical/High 的措辞里，会诱导作者过度修改，也模糊了合并决策。

反馈数量也要控制。问题很多时，优先列阻断项，次要问题归并为「后续待办」小节，而不是一次性丢几十条让人无从下手。每条反馈力求一条对应一处，不把多个问题揉进一条。

## 作者如何响应

- 逐条回应：修了 / 不修（给理由）/ 记录为待办（给触发条件）
- 不用「已同步线下讨论」搪塞
- 修复用新提交，不 squash 覆盖评审历史
- 与评审意见冲突时给出技术证据，而不是沉默接受或反复争辩

每条评审意见都要有明确去处，三种状态三选一，不能沉默跳过。标记「不修」必须给技术理由；标记「待办」必须给出触发条件（什么情况下必须处理），否则等于变相拒绝。

「已同步线下讨论」不是响应。评审要的是可追踪的结论，线下讨论如果没落到逐条回应里，评审记录就不完整。确有线下讨论的，把结论写回对应条目。

修复用新提交追加，保留评审历史。squash 会抹掉「改动针对哪条意见」的证据，事后无法追溯评审闭环。

与评审意见冲突时，用代码、测试、规格、日志等证据说话。沉默接受会掩盖真实的异议，反复争辩则消耗双方时间。一次给出证据，分歧仍存则升级，不重复拉锯。

响应完成后，把每条意见的最终状态回写到评审记录，形成「意见 → 响应 → 状态 → 证据」的闭环。评审不以「作者口头同意」结束，以「每条意见有状态、有证据、可追踪」结束。

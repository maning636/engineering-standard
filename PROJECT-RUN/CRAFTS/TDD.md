# TDD · 测试驱动的开发循环

> 工艺层第 2 篇。上游：`AGENT-PROTOCOL.md` P2；配套：`VERIFY.md`。

## 0. 一句话

**先写一个会失败的测试，再让它通过——顺序反了，测试就只是事后装饰。**

## 1. 红 → 绿 → 重构

> 三步构成一个最小循环。循环要短、要快：一次只解决一个问题。
> 红和绿的间隔越小越好；间隔越大，「顺手改」的风险越高。

### 红：先写一个必然失败的测试

**做什么**：先写一个能表达期望行为的测试；在当前实现下它必然失败。

**怎么确认**：失败信息指向「缺功能」——断言失败、被调函数不存在，而不是语法错误、导入错误或环境问题。

**常见错误**：
- 测试写到一半就运行，失败原因其实是测试本身写错（断言写反、路径不对）。
- 为了不「浪费」失败的运行，先顺手把实现也改了——红这一步就失去了意义。

### 绿：用最少的代码让它过

**做什么**：只写让红测试转绿所需的最少代码；不顺手加需求，不做重构。

**怎么确认**：该测试通过，且改动集中，没有无关文件的改动。

**常见错误**：
- 一边写实现一边改需求，失败与修复混在一起，无法判断是哪一半起作用。
- 把相邻的潜在 bug 顺手「修」了——绿这一步应该只有最小改动。

### 重构：保持绿的改结构

**做什么**：测试保持绿色，只调整内部结构（命名、抽取、去重、分层），不改行为。

**怎么确认**：改完测试仍全绿；可观察的对外行为与之前一致。

**常见错误**：
- 重构中顺手改逻辑，表面是重构其实是行为变化。
- 一次改太多，红了一时定位不到是哪一步。

> 修 bug 也走同一个循环：先写一个能复现失败的测试，再修到绿。顺序反了，修复就没有抓手。

## 2. 什么该测、什么不该测

> 测行为，不测实现。能通过公共接口观察到的，才值得写成测试。
> 能测的是接口契约和行为结果；测不了的，改设计而不是硬测。

| 对象 | 该测 | 不该测 |
| --- | --- | --- |
| 公共行为 | 输入、输出、边界、错误码 | 私有实现细节 |
| 接口契约 | 字段、类型、默认值、兼容性 | 内部调用顺序 |
| 持久化 | 写入后可读、并发冲突行为 | SQL 字符串字面量 |
| 外部依赖 | 超时、失败时的降级 | 第三方内部逻辑 |
| UI | 关键用户路径可达 | 像素级样式 |
| 配置 | 缺失、非法值的报错 | 默认值逐字 |

> 反过来：如果测试只能靠私有接口或深度 mock 才能构造出来，说明被测对象的边界没划好，先改设计，再补测试。

## 3. 例外：不强行造测试的改动

> 例外不是免测，而是换一种更轻、更对口的验证方式。
> 每一条替代验证都必须能在 CI 或命令行里复现，不能只靠「我本地跑过」。

| 改动类型 | 替代验证 |
| --- | --- |
| 文档 / 模板 / 配置注释 | 不写单测，但必须有一条可执行的验证命令（grep 断言、schema 校验） |
| 一次性脚本 | 至少跑通一次并保留输出 |
| 纯样式调整 | 截图或人工确认，写明确认路径 |

## 4. 测试质量红线

> 这五条是底线，不是建议。

- 不得为了让测试变绿而删除或弱化断言。
- 不得 mock 掉被测逻辑本身；mock 的应是外部依赖。
- 不得只断言「没抛异常」。
- 不得依赖执行顺序或共享可变状态。
- 新增测试必须能在干净环境跑通，不依赖本机残留。

> 判断标准：把实现删了，测试还绿，就是在复制实现；测试变红，才是在断言行为。

**5. 覆盖率怎么用**

覆盖率是**发现盲区的工具**，不是目标；不设百分比 KPI，也不用来考核人。

优先补关键路径与失败路径：异常分支、超时、边界值比普通成功路径更需要覆盖。纯 getter、配置映射这类一行转发不值得追——它们错不了，或者错了也测不出来。

如果一个模块覆盖率很高但线上仍出问题，说明测的是实现不是行为：断言绑死在内部结构上，行为一变就碎，行为坏了它却还绿。

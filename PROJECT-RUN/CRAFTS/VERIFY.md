# VERIFY · 完成前验证

> 工艺层第 4 篇。上游：`AGENT-PROTOCOL.md` P2/P4；相关：`AGENT-DISPATCH.md`（派发验收）。

## 0. 一句话
**跑过才算完成，形容词不算证据。**

「形容词」指「应该没问题」「看起来正常」「之前能跑」这类表述。

## 1. 完成的定义（DoD）

完成不是「代码写好了」，而是「改动被证明符合预期」。判断是否完成，唯一可靠的依据是**验收命令及其实际输出**——命令跑过、输出贴出来、结论对得上，才算完成。没有证据的「应该完成了」，一律按未完成处理。以下六项全部满足，才可声明 DoD：

- [ ] 验收命令已执行，且贴出了实际输出
- [ ] 输出与期望一致（或差异被解释并记录）
- [ ] 涉及的旧行为有回归验证（不只是新功能能跑）
- [ ] 文档与代码同步（口径变了文档要改）
- [ ] 工作区状态符合预期（没有意外的未提交/未跟踪文件）
- [ ] 涉及对外可见变化时，产品侧（版本号/变更记录）已同步

六项里任一项未达成，改动都不算完成。把「测试跑过了」当成完成、却拿不出输出原文的，等同于没跑。

为什么要先定 DoD 再动手：DoD 在开工前就写死，能防止验收标准在过程中被悄悄放宽。改动越做越大、期望越调越低，是「假完成」最常见的来源。所以 DoD 应在计划阶段确定，并随改动一并提交，评审（见 `REVIEW.md`）也以它为准。

## 2. 证据三要素

证据不是「我试了」，而是可复核的三样东西。缺一样，结论就立不住：

| 要素 | 要求 | 反例 |
| --- | --- | --- |
| 命令 | 可直接复制执行 | 「我测了一下」 |
| 实际输出 | 粘贴原文（含 passed/failed 数字） | 「测试通过」 |
| 结论 | 与期望的差异说明 | 「应该没问题」 |

「我测了一下」既没说清测了什么，别人也没法复现；「测试通过」没给数字，看不出是 3 个还是 3000 个用例通过，也看不出失败被吞掉；「应该没问题」没有任何对照依据。结论必须落到与期望的差异上：一致，就写一致；有差异，就写差异是什么、怎么处理。

三要素缺一不可：有命令没输出，等于没跑；有输出没命令，别人无法复现；有命令有输出但结论与输出对不上，说明结论没经过判断。三者齐备且相互印证，证据才成立。

## 3. 负向验证

> 本节最重要。**只测「正常能通过」，等于没测。**

验证的常见误区是只测「好事能发生」，不测「坏事被拦住」。凡改动涉及「检查、门禁、拦截、校验、过滤」类逻辑，必须故意制造一次失败，确认它真的拦住。能通过是功能，能拦住才是安全；只证明前者，等于没验证后者。

| 改动类型 | 怎么制造失败 | 期望结果 |
| --- | --- | --- |
| 新增文件检查规则 | 临时放一个违规文件 | 命令退出码非 0 |
| 新增敏感信息扫描 | 临时造一个假密钥 | 被拦截并报出文件名 |
| 新增权限校验 | 用无权限角色调用 | 403/401 而非 200 |
| 新增格式校验 | 提交一个格式错误样本 | 明确报错而非静默通过 |
| 新增「某产物必须在包内」检查 | 临时移走该产物 | 检查失败并给出修复提示 |

制造失败后，再把故障样本移除，确认正常路径不受影响。只验证「正常通过」而未验证「确实拦截」，该门禁等于没有。

负向验证的常见疏漏：

- 只造了「轻微违规」，没造「边界违规」——规则在边界处的行为往往与中间不同，要把边界样本也测到。
- 失败时只看到「报错了」，没确认「报错信息可理解」——被拦住且报错明确，才是合格；被拦住但只吐一个堆栈或空指针，等于没拦住。
- 把「被拦住」当成最终结果，没确认「用户有出路」——拦截类逻辑要同时验证失败路径的恢复与提示，不能一拦了之。

凡涉及检查、门禁、拦截、校验、过滤类逻辑的改动，负向验证是**必做项**，不是可选加分项。

## 4. 常见「假完成」清单

「假完成」是听起来像完成、实际没完成的说法。它们不指向任何证据，无法复核：

| 说法 | 为什么不算 | 实际要做什么 |
| --- | --- | --- |
| 「我改完了」 | 没跑 | 执行验收命令，贴出输出 |
| 「测试都过了」 | 没贴数字 | 粘贴测试输出原文（含通过/失败数） |
| 「应该不影响别的地方」 | 没做回归 | 运行涉及旧行为的回归用例 |
| 「接口没变」 | 没对比签名 | 对比改动前后接口签名（含类型） |
| 「文档也更新了」 | 没同步所有引用处 | 检索并更新所有引用该口径的文档位置 |
| 「用户应该能用」 | 没实机验证用户路径 | 按真实用户操作路径走一遍并记录 |

判断标准很简单：说法里没有可复核的证据，就是假完成。宁可说「还没验证」，也不要拿「应该没问题」充数。

这类说法之所以危险，在于每一条都「听起来合理」。它们都回避了同一个动作：**跑一遍并贴出证据**。识别假完成不需要专业判断，只需要追问一句「证据呢？」——问不出来的，就是假完成。

## 5. 按改动类型的验证清单

不同改动类型，验证重点不同。按下面表格选择必做项，「可跳过」只指确无此类型风险时才能省：

| 改动类型 | 必做验证 | 可跳过 |
| --- | --- | --- |
| 代码逻辑 | 单元/集成测试全绿并贴输出；改动路径的边界与错误分支 | 纯注释、纯排版改动 |
| 接口契约 | 对比改动前后签名与类型；调用方全部适配并编译/跑通 | 无对外接口的私有改动 |
| 配置与部署 | 在目标环境实际加载配置；验证开关生效、路径可解析 | 不涉及配置的改动 |
| 打包产物 | 构建产物内容与预期一致；产物内依赖齐全 | 未影响打包的改动 |
| 文档 | 与代码口径一致；所有引用处同步更新 | 无文档口径变化的改动 |
| 测试本身 | 不得为了让测试变绿而删除或弱化断言；确认测试能抓住缺陷（可故意注入缺陷验证测试会红） | 无 |

测试本身的验证要特别留意：**不得为了让测试变绿而删除或弱化断言**。测试绿的前提是代码正确，不是断言被删。验证测试有效性的办法是临时注入一个缺陷，确认测试确实变红，再还原。

按改动类型的验证遵循「就高不就低」：一次改动同时涉及多类，按最严格的类型执行，不因多数部分简单而降低标准。改动类型不好归类的（如重构），按「行为不变」作为核心标准——通过回归证明重构前后行为一致，而不是证明「重构后还能跑」。

## 6. 与发布的关系

验证是发布的前置条件，未通过验证的改动不得进入发布流程；发布前的门禁清单见 `RELEASE.md` §1。验证不是一次性的，每个里程碑都要重新验证——上一里程碑通过，不代表下一里程碑自动通过。

验证与发布是两个阶段：验证回答「改动是否成立」，发布回答「改动是否上线」。验证不过，发布流程根本不应启动，而不是「先发出去再补验证」。里程碑之间常有新增改动，所以每个里程碑都应把验证清单重新过一遍，而不是沿用上一次的结论。

# DUAL-MODE · 双模工程协议

> 一套内核 · 两种执行模式 · 预埋休眠开关  
> 适用：单人（OPC / SOLO）与小团队（TEAM）无缝切换  
> 版本：v1.0 | 2026-10-26  
> 配套：`AGENT-PROTOCOL.md` / `PROGRESS.md` / 原 engineering-standard

---

## 0. 设计原则（必读）

**不要维护两套标准。**

维护两套标准 = 迟早漂移。正确做法是：

```
┌─────────────────────────────────────────────┐
│           不变内核（两种模式完全相同）          │
│  · 10 条红线                                 │
│  · P0-P6 阶段机                              │
│  · CI 硬门 + 依赖闸门 + 安全扫描              │
│  · ADR / CHANGELOG / 版本单一真源 / 发布守卫  │
│  · 证据分级（已验证 / 已确认 / 推测）         │
└─────────────────────────────────────────────┘
                    ↓
        只有「执行层」随模式变化
┌──────────────────┐         ┌──────────────────┐
│   SOLO 模式       │  ←──→  │   TEAM 模式       │
│ · 可直推 main    │  切换   │ · PR + ≥1 人审批  │
│ · Agent 执行+互审│         │ · 人审 Agent 产出 │
│ · 自审清单       │         │ · 模块 Owner      │
│ · 发布自己负责   │         │ · 发布轮值        │
└──────────────────┘         └──────────────────┘
```

**关键洞察**：

1. 子智能体是「工具手」，不是「第二个人」。Agent 审 Agent 能换一双眼睛，但不能替代最终人类责任。
2. 团队模式需要的所有协作设施，都可以在单人阶段**预埋休眠**。切换 = 激活，而不是新建或重写。
3. 真正让切换便宜的，不是流程本身，而是单人期间持续积累的**知识资本**（ADR + pitfalls + PROGRESS/CI 历史）。

> **一句话**：单人期做的事，就是团队期要接的东西。工程体系不需要「转换为多人版本」——它需要的是不变的部分永远不变，会变的部分做成预埋的休眠开关。

## 1. 不变内核（两种模式完全相同）

以下内容在 SOLO 与 TEAM 模式下**禁止差异化**，任何修改必须走标准演进流程并通知所有相关方。

### 1.1 全局 10 条红线

1. 禁 `git add -A` / `git add .`，必须显式路径。
2. 禁 force push（除非人类显式指令，且限于未共享分支）。
3. 凭据 / cookie / 指纹 / 本地 db / 敏感运行时数据绝不入库。
4. CI 硬门不可绕过（不 skip job、不注释 gate、不改 CI 让红变绿）。
5. 依赖变更必须先在声明文件中声明，再使用。
6. 架构 / 版本策略 / 门禁规则变更必须写 ADR。
7. 协议未覆盖场景 → 写 `BLOCKED` 留人，禁止自由发挥。
8. AI 主导的 commit 末行必须带 `AI-Model: <模型名>`。
9. 不 push 到未确认的远程。
10. 文档与代码保持 LF 换行、无 U+FFFD 乱码。

### 1.2 P0-P6 阶段机骨架

```
P0 建仓 → P1 环境绿 → P2 日常开发 ↔ P3 评审 → P4 发版 → P5 运维
                                              ↓失败
                                            P6 事故处置
```

每个阶段必须具备：进入条件 / 步骤 + 验证命令 / done-when。

### 1.3 质量与知识基础设施

- CI 至少包含：test + lint + 依赖闸门 + 安全扫描（硬门）。
- 版本号单一真源 + CHANGELOG 可溯源到 commit/PR。
- ADR 目录与模板存在，关键决策必须落盘。
- 证据分级强制使用：【已验证】/【已确认】/【推测】。

这些是工程真理，与人数无关。

## 2. 执行层差异（模式相关）

| 维度              | SOLO 模式                                      | TEAM 模式                                              |
|-------------------|------------------------------------------------|-------------------------------------------------------|
| 推送路径          | 允许直推 `main`（本地四步 + 自审通过后）        | `main` 禁直推，必须走 PR                               |
| 评审              | Agent 互审 + 人类自审清单                      | PR + CODEOWNERS + ≥1 人类审批                          |
| Agent 定位        | 执行者 + 互审工具                              | 团队成员的工具；产出必须经过人类复核后才能合并         |
| 发布责任          | 自己执行 P4                                    | 发布轮值执行；技术 Owner 保留最终解释权                |
| 模块归属          | 无（或仅自己）                                 | 明确模块 Owner 名单                                    |
| PROGRESS 使用     | 唯一工作台，建议每日更新                       | 按模块或统一维护，迭代级更新                           |
| 知识同步          | 靠 ADR + pitfalls + PROGRESS                   | 增加轻量同步节奏 + 新人 onboarding 走检查单            |
| branch protection | 关闭或不启用                                   | 开启（main 要求 PR + 审批）                            |

**原则**：执行层差异必须通过模式标记显式表达，禁止在内核文档中写死某一种执行方式。

## 3. 模式标记规范

### 3.1 PROGRESS.md 头部（强制）

文件最顶部必须包含模式行：

```markdown
# 阶段: P2
# 模式: SOLO
# 更新: 2026-10-26T10:00
```

或

```markdown
# 阶段: P3
# 模式: TEAM
# 更新: 2026-10-26T10:00
```

Agent 与人类读取 PROGRESS 时，**必须先读模式行**，再决定当前适用的执行规则。

### 3.2 AGENT-PROTOCOL.md 中的标记

所有涉及「谁执行、谁审批、推送路径」的条款，必须标注模式：

```markdown
### P3 · 评审

**[SOLO]**  
Agent 互审 + 人类自审清单。本地四步全绿后可直推 main。  
自审清单见下方。

**[TEAM]**  
必须开 PR。CODEOWNERS 自动请求审查。Critical 必须修复后才能合并。  
Agent 产出的 PR 必须在描述中声明「已人工复核关键逻辑」。
```

未标注模式的条款 = 内核条款，两种模式均适用。

### 3.3 其他文件中的休眠标记

预埋但未激活的协作设施，统一使用：

```text
# [DORMANT - TEAM MODE]
# 激活方式：……
# 激活后删除本注释块
```

或单独维护休眠开关清单（见 `templates/DORMANT-SWITCHES-TEMPLATE.md`）。

## 4. 休眠开关清单（预埋项）

单人阶段就应创建并正确注释以下文件/配置，切换时只需激活。

| 休眠项                    | 建议位置                              | 激活动作                                      | 说明 |
|---------------------------|---------------------------------------|-----------------------------------------------|------|
| PR 模板                   | `.github/pull_request_template.md`   | 取消 DORMANT 注释或直接启用                   | 强制字段：问题描述、验证方式、影响范围、是否触及架构 |
| CODEOWNERS                | `.github/CODEOWNERS`                 | 填写真实 GitHub username，去掉 DORMANT 注释   | 按模块划分 |
| branch protection 规则说明| 见 `templates/DORMANT-SWITCHES-TEMPLATE.md` | 在 GitHub 仓库 Settings 中按文档开启          | main：禁直推、要求 PR、≥1 审批 |
| 模块 Owner 名单           | `docs/engineering/MODULE-OWNERS.md`  | 填入真实负责人                                | 谁负责 src/、backend/、frontend/、infra/ 等 |
| 发布轮值表                | `docs/engineering/RELEASE-ROTATION.md`| 排班并公布                                    | P4 执行人 |
| 团队 onboarding 检查单    | `docs/engineering/ONBOARDING.md`     | 启用并让新人走一遍                            | 1 天内跑通一个完整 P2-P4 |
| Agent 产出人类复核声明    | PR 模板中的必填项                     | 启用 PR 模板后自动生效                        | 防止责任真空 |

注意：branch protection 是 GitHub 仓库设置项，不是文件，单人阶段只落文档（见 `templates/DORMANT-SWITCHES-TEMPLATE.md` 第 2 节），不实际开启。

**建议在 SOLO 阶段就创建这些文件**，内容用占位符 + 清晰的 `[DORMANT - TEAM MODE]` 注释，这样切换成本接近于零。

## 5. SOLO → TEAM 切换检查单（一次性）

切换时按顺序执行，全部勾选后把 PROGRESS 头部改为 `# 模式: TEAM`。

### 硬激活（必须先完成）

- [ ] **1. branch protection 开启**  
  main 分支：禁止直推、要求 Pull Request、至少 1 人审批。  
  验证：尝试直推 main 应被拒绝。

- [ ] **1b. CI 语义切换**  
  确认 CI 同时支持 `pull_request` 触发，并把 CI job 加入 branch protection 的 required status checks（否则 PR 阶段 CI 不跑，硬门形同虚设）。

- [ ] **2. PR 模板激活**  
  `.github/pull_request_template.md` 生效，包含强制字段。  
  验证：新建 PR 时模板自动带出。

- [ ] **3. CODEOWNERS 按模块填实名**  
  去掉 DORMANT 注释，写入真实 GitHub username。  
  验证：相关路径的 PR 自动请求正确审查人。

- [ ] **4. 模块 Owner 名单公布**  
  `MODULE-OWNERS.md` 填写完成并告知全员。  
  验证：每个人都知道自己负责哪些目录。

### 软激活 + 陪跑

- [ ] **5. 发布轮值排班**  
  明确谁执行下一次 P4，技术 Owner 保留最终解释权。

- [ ] **6. 子智能体定位重申**  
  全员确认：Agent 从「执行者」降级为「团队成员的工具」。  
  Agent 产出的 PR 必须有人类声明「已人工复核关键逻辑」才能合并。

- [ ] **7. 全员通读关键资产**  
  AGENT.md 红线 + ADR 索引 + pitfalls.md。  
  新人 1 天内跑通一个完整 P2-P4 循环。

- [ ] **8. 第一次团队发版由原 SOLO 负责人陪跑**  
  第二次起可放手。陪跑目的是验证切换后流程真正跑通，而不是永远不放手。

- [ ] **9. PROGRESS 头部改为 `# 模式: TEAM`**  
  并更新时间戳。此后所有 Agent 与人类以 TEAM 规则执行。

**完成标志**：第一次团队 PR 成功合并 + 第一次团队发版成功，且无人为「流程不清楚」而阻塞。

## 6. TEAM → SOLO 反向切换（可逆）

团队解散或回到单人时，执行以下轻量操作即可，**内核完全不动**：

- [ ] 关闭或放宽 main 的 branch protection（允许直推）
- [ ] PROGRESS 头部改回 `# 模式: SOLO`
- [ ] （可选）将 CODEOWNERS / 发布轮值表重新标记为 DORMANT
- [ ] 确认 Agent 定位恢复为「执行者 + 互审工具」
- [ ] 自审清单重新成为默认评审方式

无需删除任何历史 ADR、pitfalls 或 CI 配置。

## 7. 知识资本（切换真正便宜的前提）

单人阶段真正要强制的，不是复杂流程，而是以下三样东西的**持续低成本积累**：

### 7.1 ADR（为什么这样设计）

- 只写真正改变方向的决策。
- 5–15 分钟一条即可。
- 团队成员读 ADR 就不必反复问「为什么当初这样」。

### 7.2 pitfalls.md（踩过的坑）

- 格式固定：现象 → 根因 → 修法 → 日期 → 相关 commit。
- 团队直接继承，避免重复踩坑。

### 7.3 PROGRESS 台账 + CI 绿的历史

- 记录项目实际怎么运转。
- 新人照着跑一遍就能理解当前阶段与约束。

**如果这三样在 SOLO 阶段被省掉，切换时再补，成本会陡然上升，甚至需要推倒重来。**  
反过来，只要这三样在持续积累，切换检查单里的流程激活就会非常便宜。

## 8. Agent 在双模下的行为约束

### SOLO 模式

- Agent 可读 AGENT-PROTOCOL + PROGRESS（含模式行），按当前阶段执行。
- 允许 Agent 互审。
- 最终推送前必须经过人类自审清单。
- 未覆盖场景写 `BLOCKED`，禁止自由发挥绕过红线。

### TEAM 模式

- Agent 仍然按阶段机执行，但**产出必须经由人类**。
- 任何由 Agent 创建或主要撰写的 PR，描述中必须包含人类声明：「已人工复核关键逻辑」。
- 禁止「Agent 写 + Agent 审 + 人类随手 Approve」的责任真空。
- 模块 Owner 或指定审查人对 Agent 产出负最终合并责任。

### 共通

- 始终遵守 10 条红线。
- 始终先读 PROGRESS 模式行再行动。
- AI 主导 commit 必须带 `AI-Model:` trailer。

## 10. 使用示例

### 10.1 新建项目（SOLO 起步）

1. 复制 PROJECT-RUN 核心文件。
2. PROGRESS 头部写 `# 模式: SOLO`。
3. 创建所有休眠文件并加 `[DORMANT - TEAM MODE]` 注释。
4. 按精简检查单完成 P0-P1，开始日常开发。
5. 持续写 ADR 与 pitfalls。

### 10.2 将来加人（切换）

1. 打开本文件第 5 节切换检查单。
2. 逐项激活硬开关与软开关。
3. 第一次发版陪跑。
4. PROGRESS 改为 `# 模式: TEAM`。
5. 此后按 TEAM 规则运行。

### 10.3 团队解散回单人

按第 6 节反向操作即可。

## 11. 演进规则

- 内核（红线、阶段机、硬门、ADR 要求）变更：必须走 PR，说明理由，并通知所有使用本标准的项目。
- 执行层（模式差异、休眠开关内容）变更：可在本文件内更新，保持向下兼容优先。
- 任何模式标记的新增或删除，需同步更新本文件与 AGENT-PROTOCOL。

## 12. 总结

| 原则                         | 落地方式                                      |
|------------------------------|-----------------------------------------------|
| 一套内核，永不分裂           | 红线 + P0-P6 + 硬门 + ADR 要求固定            |
| 执行层可切换                 | PROGRESS 模式行 + 协议内 [SOLO]/[TEAM] 标记 |
| 切换 = 激活，不是重写        | 休眠开关预埋 + 一次性检查单                   |
| 真正的长期资本               | ADR + pitfalls + PROGRESS/CI 历史持续积累     |
| Agent 永远是工具             | SOLO 可互审；TEAM 必须人审最终责任            |
| 可逆                         | TEAM → SOLO 只关开关，不删历史                |

**最终检验标准**：

> 当你从单人变成小团队（或反过来）时，是否只需要「激活/关闭」而不是「重写工程体系」？  
> 如果答案是肯定的，这套双模协议就成功了。

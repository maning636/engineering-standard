# 环境隔离红线（开发 / 生产永不合并）

> 立规日期：2026-11-12 · 背景：0.3.7 用户在线使用期间，开发侧多次险些影响生产
> （E1 测试窗口打到生产探针、本地施工单与生产部署混线）。
> 本规范是**硬红线**：违反任何一条即视为事故，立即停下补事故报告。

## 0. 一句话原则

**生产服务器只跑「已验收的发布物」；开发的一切活动（写码、测试、实验、子代理）只发生在开发环境。两者唯一的交汇点是「发布」这一个受控动作。**

## 1. 环境定义

| 环境 | 载体 | 用途 | 谁可动 |
|---|---|---|---|
| **开发环境** | 本机（D:\dim开发\_bidmaster）+ 本机 8031/测试库 | 写码、pytest、子代理施工、构建 | 全员/全部 Agent |
| **预发环境**（可选） | 服务器第二端口/第二 service（如 bidmaster-staging@8094） | 发布前真机冒烟 | 主模型+产品方 |
| **生产环境** | 服务器 101.43.65.216 的 bidmaster.service:8093 + nginx /bidmaster | 用户实时使用 | **仅发布流程** |

## 2. 开发期五禁（任何 Agent 任何时候）

1. **禁止直连生产**：开发/测试/子代理不得 ssh 生产执行写操作（部署脚本、改文件、重启服务）；只读探针（journalctl/status/health）需在任务书里显式授权
2. **禁止共享凭据的写路径**：开发脚本不得使用生产 SSH key 做任何非发布动作
3. **禁止在开工任务书里混入「顺手部署」**：部署永远是独立施工单，有独立验收
4. **禁止对生产库做实验**：alembic 迁移、数据订正一律先在开发库/预发跑通
5. **禁止占用生产资源做测试**：生产 nginx、域名、数据库不给测试流量

## 3. 发布是唯一交汇点（四道闸）

生产变更只允许走发布流程，缺一道即停：

1. **全量回归绿**（pytest 0 failed 0 error）
2. **产品方明确说「发布」**（聊天记录里的指令即为授权；Agent 不得自行推断）
3. **变更清单**：发布前列出本次进生产的文件/端点/迁移，产品方可见
4. **发布后验证**：health + 关键端点探针 + 用户可用性确认，异常立即回滚（保留上一版安装包与备份）

## 4. 测试流量纪律

- 需要真实服务端联调时：本机起 `BIDMASTER_PORT=8094` 的第二实例，或服务器预发实例
- E1 这类「探针打到生产日志」的教训：**联调目标写进任务书**，子代理不得自行选目标
- 服务端日志里出现开发侧 IP 的非只读请求 = 违规，主模型在台账记一笔

## 5. 数据隔离

- 生产库（laoma.db / licenses 表 / 用户数据）只读视角可用于排障，**写操作仅发布流程**
- 演示数据、测试账号、一次性脚本不进生产
- 用户激活码/授权数据：开发环境永不触碰；排障需查时用只读 SQL 并在台账记录

## 6. 违规处置

- 任何影响用户使用的事故：立即停止一切施工 → 恢复服务优先 → 事后 24h 内出事故报告（时间线/根因/防线）
- Agent 侧防线：主模型派单前自查任务书是否含生产写动作；子代理收到疑似生产写指令时**必须拒绝并上报**

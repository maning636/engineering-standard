# LICENSING · 注册码与授权服务规范

> 适用于「本地部署软件 + 授权码解锁」形态。  
> 版本：v1.0｜2026-10-28｜来源：一套已上线运行的桌面端授权体系实践

---

## 0. 一句话

**授权码管「谁能用」，机器码管「在哪台用」，服务端管「随时能停」。**  
三者缺一，授权体系就是纸糊的。

---

## 1. 先选模型：三种授权形态

| 形态 | 原理 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| **A. 纯离线签名** | 服务端签发带签名的授权串，客户端离线验签 | 完全离线可用；实现最简 | **无法停用**；泄露即失效 | 一次性买断、无售后要求 |
| **B. 纯在线校验** | 每次启动向服务端验权 | 可控性最强 | 断网即停摆；服务器成本 | SaaS、强管控场景 |
| **C. 混合（推荐）** | 激活时联网换签名 token；平时离线验签；定期刷新 | 离线可用 + 可远程停用 | 需设计降级策略 | 本地部署商业软件 |

**推荐 C**：激活联网一次，之后凭 token 离线运行；token 到期前自动续期；服务端停用后，最迟在下一个刷新周期失效。

**关键设计参数**（按实际调整）：

- token 有效期：**7–14 天**（越长越难停用，越短越频繁联网）
- 刷新提前量：到期前 **1/4 周期**开始尝试续期
- 离线宽限：连续刷新失败 **N 天**（建议 7–15 天）后降级为**只读**，不直接锁死——避免客户断网停摆引发投诉

## 2. 数据模型（最小可用）

```sql
-- 授权码主表
CREATE TABLE licenses (
  code            TEXT PRIMARY KEY,          -- 授权码明文（分组随机串）
  customer        TEXT NOT NULL,             -- 客户标识（公司/联系人，用于对账）
  status          TEXT NOT NULL,             -- inactive | active | disabled | expired
  expires_at      TIMESTAMP NOT NULL,        -- 授权到期时间
  machine_id      TEXT,                      -- 首次激活绑定的机器码（NULL=未激活）
  activated_at    TIMESTAMP,
  last_seen_at    TIMESTAMP,                 -- 最近一次心跳/刷新
  max_users       INTEGER DEFAULT 1,         -- 允许的账号数（企业版 >1）
  user_ids        TEXT,                      -- JSON 数组：已绑定的用户 id
  assigned_user_id TEXT,                     -- 单人版直接绑定
  assigned_at     TIMESTAMP,
  note            TEXT                       -- 备注（销售渠道/合同号）
);

-- 审计表：授权动作必须留痕（谁、何时、对哪张码、做了什么）
CREATE TABLE license_audit (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  action      TEXT NOT NULL,     -- create | activate | refresh | disable | enable
  code        TEXT NOT NULL,
  actor       TEXT,              -- 操作人（管理员用户名）
  detail      TEXT,              -- JSON：机器码/原因/IP 等
  created_at  TIMESTAMP NOT NULL
);
```

**设计要点**：

- `code` 用**分组随机串**，不要自增或可推导：`XXXX-XXXX-XXXX-XXXX-XXXX`，字符集去掉易混淆的 `O/0/I/1/L`
- `status` 与 `expires_at` **双重判断**：状态为准，到期时间兜底（防忘记手动停用）
- `user_ids` 用 JSON 而非关联表，是为了让「一码多账户」保持单表可查；若需要复杂查询再拆表
- 审计表只追加，不更新不删除

## 3. 激活流程（时序）

```
客户端                          授权服务端
  │                                │
  ├─(1) 生成 machine_id（本地持久化，不联网）
  ├─(2) POST /activate {code, machine_id}
  │                                ├─ 校验 code 存在 / status=inactive
  │                                ├─ 校验 expires_at 未过期
  │                                ├─ 绑定 machine_id（已绑其他机器 → 409）
  │                                ├─ status=active，写审计
  │  ←─(3) {token, expires_at}     │
  ├─(4) 本地存 token，启动时验签（离线）
  │                                │
  ├─(5) 到期前 1/4 周期：POST /refresh {token, machine_id}
  │                                ├─ 验签 + 查 status
  │  ←─(6) 新 token                │
  ├─(7) 刷新失败累计 N 天 → 降级只读
```

**必须处理的边界**：

| 场景 | 期望行为 |
|---|---|
| 码不存在 / 已停用 / 已过期 | 明确错误码，文案区分（不要统一「授权失败」） |
| 码已绑其他机器 | `409`，提示联系客服换绑（**不要静默覆盖**） |
| 同一机器重复激活 | 幂等，返回新 token |
| 刷新时机器码不匹配 | 拒绝续期（防 token 拷贝到别的机器） |
| 服务端 5xx / 网络超时 | **不立即锁死**，按离线宽限继续可用 |

## 4. Token 设计

**推荐：服务端私钥签名，客户端只嵌公钥。**

```
payload = {
  "code": "<授权码>",
  "machine_id": "<绑定机器>",
  "exp": <Unix 时间戳>,
  "iat": <签发时间>,
  "max_users": <可选，用于企业版>
}
token = base64(payload) + "." + signature(payload, PRIVATE_KEY)
```

**红线**：

1. **私钥只存在服务端**，永不下发、永不入库、永不进客户端安装包
2. 客户端只嵌**公钥**；验签失败一律拒绝
3. `machine_id` 必须参与签名——否则 token 可被拷到任意机器使用
4. token 里带 `exp`，客户端也检查（不依赖服务端时钟）
5. 算法选型：ED25519（短、快、无参数坑）或 ECDSA P-256；**不要用对称密钥**（客户端可逆出密钥）

**机器码怎么生成**（三选一，按隐私要求）：

| 方案 | 做法 | 特点 |
|---|---|---|
| 硬件指纹哈希 | CPU+主板+磁盘序列号 拼哈希 | 稳定，但涉及隐私，需在协议里说明 |
| 随机 UUID | 首次运行生成并持久化 | 最友好；重装系统会变，需换绑流程 |
| 混合 | 随机 UUID 为主，硬件指纹为辅（仅异常检测） | 推荐：不采集敏感信息也能防盗拷 |

> 不要在机器码里包含用户名、主机名、路径等可识别信息，也不要上传。

## 5. 多用户（企业版：一码多账户）

目标：一个授权码 → 同机多账号 → 共享业务数据。

**实现要点**：

- 授权表加 `max_users`（默认 1）与 `user_ids`（JSON 数组）
- 新用户注册/绑定时校验：`len(user_ids) < max_users`，超员返回 `422` 并说明上限
- **数据共享语义要明确定义**（推荐「读通写隔离」）：
  - 同租户（同一 license 的 user 集合）内的用户**互相可见**业务数据
  - 写操作仍归属具体用户；管理员可越权
- 管理员角色（`admin`）**不参与租户共享**，保持全量可见

**反例（踩过的坑）**：把所有数据的过滤条件从 `user_id == current` 直接改成「同租户可见」，会破坏管理员原有的「看全部」语义——必须为管理员单独短路。

## 6. 角色边界：客户端禁 admin 登录

**规则**：`admin` 角色只在**服务器管理后台**登录；客户端一律使用普通 `user` 角色。

**原因**：管理员权限只应存在于服务端受控环境；若允许客户端 admin 登录，等于把后台能力下发到每台客户机。

**实现**：登录接口在「客户端模式」（连远程服务）下，识别到 `role == admin` 直接拒绝，并给出可操作提示：

```
管理员账号无法在客户端登录，请使用服务器管理后台。
如需客户端使用，请创建普通用户账号。
```

> 这条要写进产品文档与客服话术，否则用户会以为是 bug。

## 7. 密钥管理红线（不可协商）

| 项 | 规则 |
|---|---|
| 签名私钥 | 只存服务端；权限 `600`；**不入 git、不进安装包、不上传任何第三方** |
| Windows 开发机 | `os.chmod(0o600)` 在 Windows 不生效（实测仍为 666）。**私钥应在 Linux 服务器生成**；必须在 Windows 生成时用 `icacls <file> /inheritance:r /grant:r %USERNAME%:R` 限制为只读 |
| 密钥备份 | 离线介质 + 加密；备份文件本身不写明文口令 |
| 轮换 | 私钥泄露立即轮换：新公钥随下一版本客户端发布，旧 token 设过渡期 |
| 客户端 | 只嵌公钥；公钥可公开，不属于秘密 |
| 环境变量 | 私钥路径用变量引用（如 `LICENSE_PRIVATE_KEY_PATH`），**不要把密钥内容写进 env** |
| 日志 | 任何日志不得打印私钥、token 全文、密码哈希；只打印前 8 位或哈希前缀 |

**检查方法**（发布前必跑）：

```bash
# 1. 安装包里不能出现私钥/种子
grep -rIl --binary-files=text "BEGIN.*PRIVATE KEY" <解包目录> || echo "OK"
# 2. 仓库历史里不能有私钥
git log -p --all | grep -c "BEGIN.*PRIVATE KEY"   # 期望 0
# 3. 客户端产物里只应出现公钥
grep -rIl "PUBLIC KEY" <解包目录> | head
```

## 8. 停用、续期与审计

- **停用**：`status=disabled` → 下次 refresh 即拒；给出「授权已停用，请联系服务商」文案
- **延期**：改 `expires_at`；已激活的客户端在下次 refresh 生效
- **换绑**：清空 `machine_id` 并写审计（记录原机器码与操作人）
- **批量操作**：按 `customer` 前缀筛选后批量改状态，逐条写审计
- **对账**：按 `customer / status / expires_at` 出报表，与销售合同对齐

**审计必须回答三问**：谁改的、什么时候、改前是什么。

## 9. 交付与合规

- **源码交付义务**：若产品使用 AGPL/GPL 类许可，授权交付时必须同时提供**同版本**源码（版本号一一对应，不可「先给安装包、源码以后再给」）
- **交付记录**：每张码交付了哪个版本要登记（版本 + 日期 + 渠道），便于事后举证
- **不公开分发**：内测或定向销售期，安装包与源码**不挂公开下载区**；改为凭授权定向提供（详见发布规范）
- **隐私**：机器码生成规则、心跳上报字段（建议只报 `code + machine_id + version`）要在隐私条款里写明

## 10. 常见坑（实测）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 客户端登录 `405 Method Not Allowed` | 反向代理转发时**没剥前缀**：`/app/api/x` 原样转发，后端只认 `/api/x` | 代理配置 `proxy_pass http://127.0.0.1:PORT/api/;`（带 URI） |
| 2 | 用管理员账号登录客户端被拒 | 设计限制（见 §6） | 创建 `user` 角色账号；把这条写进客服话术 |
| 3 | 停用授权后客户端仍能用很久 | token 有效期太长（如 30 天）且无强制心跳 | 缩短到 7–14 天；或加「启动时异步校验」 |
| 4 | 换电脑后无法激活 | `machine_id` 已绑定且未设计换绑 | 提供换绑接口（清空 `machine_id` + 审计） |
| 5 | 服务器重启后所有客户端掉授权 | 状态存在内存/未持久化 | 状态与到期时间必须落库 |
| 6 | 多用户改造后管理员看不到全部数据 | 租户过滤覆盖了管理员分支 | 管理员短路（见 §5 反例） |
| 7 | 源码包与安装包版本不一致 | 发布时先打包后改码 | 发布前强制校验版本号一致，不一致拒绝发布 |

## 11. 验收清单（上线前逐项过）

- [ ] 激活：正确码可激活；错误码/停用码/过期码返回**不同**错误文案
- [ ] 绑定：第二次在另一台机器激活被拒（409），且原机器仍可用
- [ ] 离线：拔网线后能正常使用；token 到期后按宽限策略降级，不直接崩溃
- [ ] 停用：服务端停用后，客户端在 ≤1 个刷新周期内失效
- [ ] 续期：到期前自动续期成功；续期失败有明确提示
- [ ] 多用户：超出 `max_users` 的注册被拒；同租户数据互相可见；管理员看全部
- [ ] 角色：admin 在客户端被拒且提示可操作
- [ ] 密钥：三项检查全过（安装包无私钥 / git 历史无私钥 / 客户端只有公钥）
- [ ] 审计：create/activate/refresh/disable 四类动作都有记录，含操作人
- [ ] 合规：源码与安装包版本一一对应；交付记录可查

**负向测试必做**：以上每一条「拒绝」类行为，都要故意制造一次失败来验证，而不是只看「正常能通过」。

# REQUIREMENTS · 需求追踪与变更控制

> 项目层规范。上游：`opc-playbook/skills/client-requirements`（客户项目，产出 prd.md）或 idea-to-cash 第 3 关 vdf、第 6 关 blueprint（自有产品）。下游：`ORCHESTRATION.md`（任务图）、`CRAFTS/ACCEPTANCE.md`（UAT）、`CRAFTS/VERIFY.md`（证据）。
> 签约客户项目在 P2 接受并锁定 H2；自有产品探索和一次性原型可先用轻量需求，不强制完整 H2。H2 状态与映射以 opc-playbook 的 `client-requirements/references/handoff.md` 为准。

## 0. 一句话

**需求要有编号，每条需求都能查到是谁写的、哪个测试证明了它、客户是否认可；需求怎么改，也要留下记录。**

本文件是需求编号格式、需求状态和变更流程的唯一权威出处。其他文件只引用这里，不重复定义。

## 1. 编号

| 类型 | 格式 | 例子 |
|---|---|---|
| 功能需求 | `<业务ID>-F<两位>` | `REQ-2026-0001-F03` |
| 非功能需求 | `<业务ID>-N<两位>` | `REQ-2026-0001-N01`（检索响应 P95 < 2 秒） |
| 验收用例 | `<需求编号>-A<两位>` | `REQ-2026-0001-F03-A01` |
| 变更提案 | `CP-<业务ID>-<两位>` | `CP-REQ-2026-0001-02` |

- 业务 ID 来自 `opc-playbook` 的 `bizid.mjs`，不另起一套。
- 项目内部可以简写为 `F03`、`F03-A01`，跨项目、跨库引用时必须写全称。
- client-requirements 的 F 编号沿用，不重新编号；其 `scope.md` 中“`A01` + 需求列 `F03`”转换为 `F03-A01`，跨库再补全业务 ID，已是组合形式的不得重复拼接。
- 优先级映射：`P0 → 必须`、`P1 → 应该`、`P2 → 可以`、出范围项 → `本期不做`。追踪脚本只识别本文件的 MoSCoW 术语。
- **编号发出后不复用。** 需求删除时把状态改为“作废”，保留这一行。

## 2. 每条需求必填

字段见 `templates/REQ-TEMPLATE.md`：编号、标题、来源、优先级、验收标准（至少 1 条）、依赖、状态、确认人和日期。

**来源**写客户原话的出处，例如纪要路径加行号，或者访谈对象加日期。写不出来源的需求不能进入“已确认”。

## 3. 验收标准格式

```
AC-1  给定 <前置条件>
      当   <用户动作>
      那么 <可观察结果>
```

可观察结果要写到能判断对错为止。

- 禁止写“体验好”“速度快”“稳定”“智能”。要换成数字或者看得见的行为，例如“列表 1000 条数据时首屏 < 1.5 秒”“断网时提示‘已离线，数据将在恢复后同步’”。
- **AI 类需求**不能只写“回答正确”，要写成：在评估集 `<路径>` 上，`<指标>` ≥ `<阈值>`，并且写明兜底行为（低置信度时怎么处理）。评估集的格式见 `CRAFTS/EVAL.md`（G3）。

## 4. 优先级（MoSCoW）

| 级别 | 含义 | 规则 |
|---|---|---|
| 必须 | 缺了就不能验收 | 追踪表这一行不能有空列，否则 P4 不能发版 |
| 应该 | 本期计划做 | 没做完要在验收报告里说明 |
| 可以 | 有余力再做 | 不进入报价承诺 |
| 本期不做 | 明确排除 | 写进出范围清单，以后防范围蔓延靠它 |

## 5. 状态流转

```
草稿 → 已确认 → 已实现 → 已验收
  └────────┴────────┴──→ 作废（任何状态都可以，保留记录）
```

| 转换 | 条件 | 谁来做 |
|---|---|---|
| 草稿 → 已确认 | 有来源，验收标准合格，客户方确认人签名（邮件或聊天截图都算） | 项目负责人 |
| 已确认 → 已实现 | 追踪表里的任务、测试、证据列都已填写，测试通过 | 工程层（合并门通过后） |
| 已实现 → 已验收 | UAT 用例通过，验收报告里有这条需求 | 客户验收人 |
| 任意 → 作废 | 有对应的变更提案（CP）并已批准 | 拍板人 |

“已确认”之后，验收标准的任何修改都必须走第 7 节的变更流程，**不能直接改文字**。

## 6. 追踪表

模板见 `templates/TRACE-MATRIX-TEMPLATE.md`。每个项目一张表，放在 `docs/requirements/TRACE-MATRIX.md`。

规则：
- 每条需求一行，“作废”的需求保留这一行，结论列写“作废 CP-xx”。
- “必须”级需求在发版前，设计、阶段、任务、测试、证据五列都要填上。
- 机判命令：`node scripts/orchestrate/trace-check.mjs docs/requirements/TRACE-MATRIX.md`。有空列时返回非零，P4 发版前必须跑这条命令。
- 加上 `--stage release` 后，还会检查“必须”级需求的验收结论列不能为空（用在验收之后）。

## 7. 变更控制

需求在“已确认”之后发生的任何变化，都要走变更提案（模板 `templates/CHANGE-PROPOSAL-TEMPLATE.md`）：

1. 谁提的都要登记，包括客户口头提的、开发自己发现的、验收时冒出来的。
2. 先做影响分析：涉及哪些需求、哪些设计和契约、哪些任务和测试，工期和费用各变多少。
3. 判断是否超出合同范围。**超出的必须先报价**，交给人拍板（G6）。
4. 决定只有三种：同意、拒绝、转二期。同意后，受影响的任务在任务图里重新标记为 `ready`，契约有变化的同时走 `CONTRACT-CHANGE`（见 `ORCHESTRATION.md`）。
5. 开发过程中不允许“顺手加一点”。合并门只验证任务是否已在可信基线登记、授权字段和 write_scope 是否越界，不能证明 CP 已获业务批准。需求变更必须另有 CP 记录；追踪核对发现无 CP 的新增需求时，退回经营/项目负责人，不得靠修改任务图补授权。

## 8. 和其他文件的关系

- `templates/BUILDSPEC-TEMPLATE.md`：每个阶段列出本期覆盖的需求编号。
- `CRAFTS/VERIFY.md`：证据三要素中的“对应什么”统一填需求编号。
- `ORCHESTRATION.md`：任务图里每个任务的 `req` 字段必须引用这里的编号。
- `CRAFTS/ACCEPTANCE.md`：UAT 用例由验收标准派生，用例编号是 `<需求编号>-A<两位>`。

## 9. 借鉴边界

spec-kit、OpenSpec、BMAD-METHOD、Kiro specs 都有完整的需求流程。这里只借三件事：编号、“给定/当/那么”格式的验收标准、变更提案。它们的目录结构和命令不引入，避免和 idea-to-cash、client-requirements 冲突。

# DEPLOY 部署模板说明

## 1. 本目录用途

本目录存放 nginx 反向代理配置示例与部署校验清单。

- `nginx-reverse-proxy.conf.example`：可修改的反向代理配置示例，用于单产品挂在主站子路径下的场景。
- 实际使用的配置必须入仓（放在 `docs/deploy/nginx/` 或本目录），服务器只是运行环境，配置以仓库为准。

## 2. 三个必踩的坑

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| `proxy_pass` 不带 URI | 返回 405 | `proxy_pass` 末尾必须带 `/api/`（或对应路径），让 nginx 只替换前缀 |
| `alias` 与 `location` 尾斜杠不一致 | 404 或路径拼接错误 | `location` 与 `alias` 的尾斜杠必须成对一致（都带或都不带） |
| 父目录缺 `x` 权限 | 返回 403（不是 404） | 用 `namei -l <path>` 检查每级父目录都带 `x` 权限 |

## 3. 部署四步

1. **备份**：备份服务器上的原配置（带时间戳，见第 5 节）。
2. **上传/编辑**：把仓库里的配置上传到 nginx `conf.d/`（或对应 include 目录），按实际域名、端口、路径修改。
3. **语法检查**：`nginx -t` 必须通过。
4. **重载**：`nginx -s reload`。

> 强调：reload 之前必须先 `nginx -t` 通过，否则错误配置会被加载，导致服务异常。

## 4. 部署后验证清单

```bash
# 1. 首页 200
curl -i http://127.0.0.1/app/          # 期望 200

# 2. API 健康 200
curl -i http://127.0.0.1/app/api/health # 期望 200

# 3. 登录接口（POST 错误凭据）401
#    说明：能拿到 401 说明路由已通；401 是凭据错误，不是路由错误。
#    若返回 404 或 405，说明反代配置有误（见第 2 节）。
curl -i -X POST http://127.0.0.1/app/api/login -d '{"u":"x","p":"x"}' -H 'Content-Type: application/json'   # 期望 401

# 4. 静态资源 200
curl -i http://127.0.0.1/app/static/app.css   # 期望 200

# 5. 下载目录（若有）200 或 403
#    200 表示可访问；403 说明缺权限，需检查父目录 x 权限（见第 2 节）。
curl -i http://127.0.0.1/app/downloads/      # 期望 200（或 403 需查权限）
```

## 5. 回滚

- 备份文件保留带时间戳的命名，例如 `nginx.conf.bak-20261028_193000`，不覆盖旧备份。
- 回滚 = 恢复备份文件 → `nginx -t` → `nginx -s reload`。

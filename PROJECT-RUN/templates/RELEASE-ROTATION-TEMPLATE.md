## 1. P4 发版职责清单（每次必做，约 30-60 分钟）

1. **版本号**：确认版本单一真源已更新（如 `pyproject.toml` / `package.json` / `go.mod` 等，按项目实际），多处一致。
2. **CHANGELOG**：从最近一个 tag 起，收集所有合入 commit / PR，写入 `CHANGELOG.md`，含破坏性变更标记。
3. **执行发布脚本**：
   ```bash
   <发布脚本> --version vX.Y
   ```
   产出：构建包 + 校验文件（`.sha256` / `.sig`）+ 部署元数据。
4. **验证发布物**：
   - 校验产物 SHA256 与本地 `.sha256` 逐字符一致。
   - E2E 冒烟：全新环境安装 → 启动 → 走通关键路径 → 通过。
   - 升级路径：v(N-1) → v(N) 无数据丢失。
5. **旧包保留**：`release_v<N-1>/` 与对应校验文件保持可访问，不覆盖、不删除，用于回滚。
6. **公告**：更新 `docs/engineering/PROJECT-RUN/PROGRESS.md`，在 `release_vX.Y/` 旁写一份「本版改动摘要」。

- 每次发版间隔 ≥ 3 天，避免疲劳发版。
- 同一人**连续**负责不超过 2 次，第 3 次强制换人（防止单人知识孤岛）。

## 3. 技术 Owner 保留最终解释权

- **技术 Owner**（当前：`<待填>`）对发布窗口、版本号跳变、回滚决策**保留最终解释权**。
- 轮值人只负责**执行**发布流程，不决策「发不发、何时发、发哪个版本」。
- 出现以下情况，技术 Owner 可直接叫停并回滚：
  - 生产事故（用户数据损坏 / 授权异常 / 数据泄露）
  - 依赖或安全审计红灯
  - CI 未过或 required check 缺失
- 叫停后 24 小时内必须在 `docs/pitfalls.md` 追加一条 P-NNN 记录，含根因与修法。

## 4. 回滚预案

1. 恢复 `release_v<N-1>/` 到发布路径（对象存储 / CDN / 落地页）。
2. 落地页 `index.html` 与校验文件同步回滚到 v(N-1) 版本。
3. 公告：在团队渠道 + 用户群同步「v(N) 已下线，请使用 v(N-1)」，附 SHA。
4. 在下一版 release notes 里显式列出「v(N) 已作废，改动未合入主干」，避免考古时误导。
